# 落とし穴カタログ — 症状・真因・それを塞いでいる場所

指示書14章の29件に、**このリポジトリのどこがそれを防いでいるか** を対応づけたもの。

移植時のチェックリストとして使うほか、「このガードは何のためにあるのか」を後から
辿れるようにするのが目的である。**8.5 の教訓** — 除外や例外の理由を残さないと、
後から「抜けている」と誤って埋め戻される — をリポジトリ規模で適用したもの。

凡例: ⛔ = コードで構造的に塞いだ / ⚠️ = 検知して報告する / 📋 = ラダーの手順で防ぐ

## この表の使い方

新しいガードを足したら **ここに1行足すこと。** 逆に、ここに載っているガードを外す
提案が出たら、対応する症状が再現しないことを確認してからにする。

指示書14章の29件のうち、**このリポジトリで「構造的に塞いだ」と言えるのは⛔の行だけ**
である。📋 の行はラダーの手順に依存しており、手順を飛ばせば再現する。⚠️ の行は
検知するだけで、対処は人間が行う。

## 対象条件の全廃 (2026-08-12)

運用者の指示「**ビズリーチで設定していた条件は全て忘れてください**」により、
指示書15章から持ち込んだ対象条件を **ルールごと削除** した。

| 削除したルール | 対応していた事故 |
|---|---|
| `age` | — (年齢は媒体側の検索条件が持つ) |
| `longest_tenure` / `current_tenure` | 7.1 (勤続年数の判定不能が隠れる) |
| `job_change_count` | 7.5 (現職の二重計上) |
| `education` / `domestic_university` | 6.5 (学歴の写像漏れ) / 7.4 (カタカナ大学名) |
| `foreign_native` | 7.2 (日本人を外国人として誤除外) |

残っているのは `membership_status` だけである。対象の定義は媒体側の検索条件
(座標 `nav.candidate_list_url`) が持つ。

### なぜ「無効化」ではなく「削除」なのか

閾値を寛容な値に書き換える形 (`age_min: 0`、`job_change_threshold: 999`) は、
**7.6 の事故そのもの** である。設定を読んだ人に「意図して外した」と「打鍵ミス」の
区別が付かず、外したはずのルールが除外レポートと監査出力に **有効な安全弁として
出続ける**。フィールドごと消せば、無いものは無いとしか読めない。

`extra="forbid"` があるので、古い設定を持ち込むと未知のキーとして読込時に落ちる。
消えたフィールドが黙って復活する経路は無い。

### この削除で失われたもの (**意図的に記録する**)

- **7.1 の再現テストが消えた。** 「最長勤続の MATCH が現職在籍の判定不能を隠す」
  という具体的な再現は勤続ルールと共に消えた。不変条件そのもの (一致した判定が
  別の判定不能を覆い隠さない) は `tests/targeting/test_filter.py` で **合成ルールを
  使って書き直してある** — 特定のルールの性質ではなく集約の性質なので、むしろ
  ルール本数から独立した形になった
- **8.5 の非対称性を守るテストが消えた。** 「学歴だけ include」という業務判断を
  「揃っていないのは間違いだ」と直されないよう固定していたテストは、学歴ルールごと
  消えた。方針が1本しか無い今、非対称性を実行可能な形で示す場所は無い。
  **これは記録として残すしかない劣化である**
- **7.2 の適用範囲テストが消えた。** 「語学判定は語学欄だけを見る」を AST で
  検査していたが、検査対象のルールが無い。**通るだけのアサーションとして残さず
  削除した** — 意味を失った緑は、消えた赤より悪い

復活させる場合は `rules.py` と `undeterminable_policy` の **両方** に足すこと。
片方だけでは registry の両方向検査が起動時に落ちる (それが仕様である)。

## 「常に真になる目印」を3度作り込んだ (2026-08-13)

段階2の座標 `nav.list_ready_selector` に、`scout recon observe-list` が
**`body.c-body`** を推奨した。実際に本番画面へ実行して発覚した。

`nav.list_ready_selector` は「候補者一覧の描画完了」を表す要素で、
`wait_for_selector` がこれを待つ。`body.c-body` は全ページに常時あるので、
待機は常に即座に成功する。**一覧が描画される前に走査して0件と読み、静かに終わる** —
原則2の「最も危険な失敗は例外ではなく静かなゼロ件」そのものである。

### 同じ型のバグが3度出ている

| 回 | 場所 | 推奨してしまった値 | なぜ常に真か |
|---|---|---|---|
| 1 | `auth.success_marker_selector` | `a.c-link` | 汎用ユーティリティクラス。ログイン前の画面にもある |
| 2 | 同上 (再発) | — | `login_form_visible` が待たない API を使い、描画前を「無い」と読んだ |
| 3 | `nav.list_ready_selector` | `body.c-body` | 全ページに常時ある枠 |

**共通の原因は「不在で判定する目印を、存在の頻度だけで選んだ」こと。**
1回目は「一致件数が少ない順」に並べ替えて直した。しかしそれは *順位付け* であって
*排除* ではない。今回、比較対象を「結果ありページ」と「0件ページ」の2枚にしたところ、
枠は両方に等しく存在するので差が0となり、最優先に躍り出た。

**順位付けで後ろに回すだけでは足りない。** 運用者は「別案」の一覧から選べてしまうし、
今回は先頭そのものが枠だった。構造的に候補から外す必要がある。

### 併発した2つ目の欠陥

`nav.drawer_close_selectors` を得るために「行」をクリックする実装で、行の選定を
**出現回数が最多のトークン** で行っていた。1枚のカードに10個ある文字要素
`p.c-search-member-card-text` が、25個しかないカード本体
`div.c-search-member-card` に勝ち、文字をクリックして「何も開かなかった」で終わった。

**「最も多く繰り返されるもの」は行ではない。** 行の *中身* である。

### 運用者の再実行は有限である

開発コンテナから媒体へ到達できないため、検証は運用者が GitHub Actions で行う。
つまり **バグ1つにつき運用者の往復が1回増える**。「動かして直す」が使えない以上、
出す前に反証を通す必要がある。この修正は設計案を3つ立て、それぞれを3つの観点
(常に真にならないか・0件で消えないか・推測していないか) で反証してから実装した。

### 続き: 直した述語の下で、行の同定が壊れた (2026-08-13 同日)

述語を反転した版を運用者が実行したところ、今度は **行が `div.c-segment` (2個) と
誤判定された**。実際の行は `div.c-search-member-card` (25枚) である。

```
nav.list_ready_selector: UNRESOLVED
  # 行は同定できました: div.c-segment (2 個)
  # 0件ページの試行:
  #   - age: 使えません — 行が 1 個ありました (0件になっていません...)
  #   - pagination: 使えません — 行が 1 個ありました (...)
```

原因は2つ重なっている。

**1. 極大性の規則を、絞り込みより先に掛けていた。**

`maximal_groups` は「親が別の群の要素の内側にある群」を落とす。これは *内側* を
落とす規則なので、素朴に全群へ掛けると **最も外側の繰り返し群だけが残る**。
画面には `div.c-segment` が2つあり (検索条件パネルと一覧の区画)、カードの親は
その内側なので、カード群が「極大でない」として落ちた。

当初この順序を選んだ理由は「カード群が0件フィルタに落ちたとき、カードの中の列が
繰り上がるのを防ぐ」だった。防ぎたかったものは実在するが、**代償の方がはるかに
大きかった** -- 一覧と無関係な外側の繰り返しが1つでもあれば必ず勝つ。

先に「0件検索で消える」で絞れば `c-segment` はそこで落ちる (0件ページにも残るため)。
残った中で極大を取れば、カードが文字要素に勝つ。**これが本来したかった比較である。**

**2. 0件ページの妥当性検査が、行の同定結果に依存していた。**

「選ばれた行トークンがこのページに何個あるか」で0件かを判定していたため、行を
誤ると **0件ページまで巻き添えで捨てられる**。実際、`c-segment` が0件ページにも
1個あったので、2枚とも「0件になっていません」と拒否され、何も確定しなかった。

行が正しいかに関わらず「結果ページで繰り返していた群のどれかが消えた」は観測できる。
判定をそちらへ移した (`vanished_group_count`)。

### この2件から取れる教訓

- **「内側を落とす」規則は、止める境界を決めないと最上位まで伝播する。** 極大性の
  ような相対的な規則は、先に絶対的な条件 (0件で消える) で母集団を絞ってから掛ける
- **検査の前提を、その検査の結果に依存させない。** 0件ページの妥当性が行の同定に
  依存していたため、1つの誤りが2つの観測を同時に潰した。独立に観測できる量
  (何かが消えたか) で判定すれば、誤りは片方に閉じる
- 1回目の修正は「値が枠にならないこと」を構造的に保証した。**その保証は今回も
  効いていた** -- 誤った行が選ばれても、値は出ずに UNRESOLVED になった。
  静かに間違った値を書くよりはるかに良い。不変条件は狙いどおり働いている

### 続き: 反証が3つ目の欠陥を、運用者に届く前に捕まえた (2026-08-13 同日)

2度目の修正を運用者へ送る前に、3つの観点 (順序反転の副作用・0件判定の新条件・
クリック対象) で反証にかけた。**2つが反証成立し、再現もできた。** 送っていれば
3度目の失敗になっていた。

**欠陥1: 極大性が単調でなくなった。**

`maximal_groups` は「他の群の要素の内側に親がある群」を落とす。**支配者 (カード群)
が候補集合から先に消えると、その子孫が繰り上がって極大になる。** 1回目の修正が
「行 > 行の中身」を無条件に保証していたのは極大性を全群に掛けていたからで、順序を
反転した結果、その保証は「カード群が0件フィルタを通過したときだけ」の条件付きに
なった。汚染された0件ページを1枚採用するだけで、行が `p.c-search-member-card-text`
になり、**UNRESOLVED ではなく推奨値として出た**。

**欠陥2: 「消えた群が1つでもあるか」は緩すぎた。**

修飾クラス `div.c-search-member-card--scouted` は独立のトークンなので、カードが25枚
表示されたままのページでも「スカウト済みが0枚」で合格する。さらに悪いことに、
**この指標は「描画されていないほど高くなる」** -- 何も描画されていないページで最大に
なる。読み込み中の骨組み `div.c-loading` が0件表示として採用されると、本番では行より
先に出るので `wait_for_selector` が一覧の描画前に成功する。**塞いだはずの静かなゼロ件
が、新しい経路で完全に復活していた。**

**欠陥3: 記入例が枠を勧めていた。**

0件ページが1枚も使えなかったとき、誤判定された行のまま
`"div.c-segment, <0件表示のセレクタ>"` という記入例を印字していた。`c-segment` は
描画前から常に在る。**運用者が指示どおり貼れば、常に真になる目印が座標に入る。**
潰すはずの失敗を、こちらから勧めていたことになる。

### 対処

- 0件ページの判定を「最も重い繰り返し群が0個であること」に変えた。この量は行の同定
  より前に、結果ページだけから決まる。修飾クラス1つでは満たせず、カードが残っている
  ページは必ず落ちる。近似が外れても UNRESOLVED = 見える失敗に倒れる
- 0件ページを **落ち着く前にもう1枚撮る**。そこに既に在ったトークンは0件表示の候補から
  外す。読み込み表示は遷移直後から在り、本物の0件表示は応答後に出る -- この時間差は
  観測できるので、推測せずに切り分けられる
- 確認できていない行の記入例は印字しない。参考として構造は出すが「そのまま座標に
  書かないでください」と明示する

### この回から取れる教訓

**「動かして直す」が使えない場所では、反証にかける方が安い。** この修正は運用者の
往復を1回節約し、しかも節約した1回は「静かに間違った値を貼る」回だった。3つの欠陥は
どれもテストが緑のまま存在していた -- 自分で書いたテストは、自分が想定した失敗しか
検査しない。


### 続き: variant電池が4つ目の欠陥を、実機の前に捕まえた (2026-08-13 同日)

反証への対処として入れた「最も重い繰り返し群」の0件ページ判定が、**それ自体
入れ子に弱かった**。部分木の重さは外側を優遇する -- 一覧を *囲む* 区画
(`div.c-segment` ×2) が中身ごと数えられてカード25枚より重くなり、正常な
0件ページを2枚とも拒否した。

今回はこれを **実機ではなく手元で** 見つけた。「次の実行で起こりうる画面の形」を
fixture として列挙するテスト (`tests/recon/test_analyze_variants.py`) を書いたところ、
いちばん素直な理想形がいきなり落ちた。運用者の往復は消費されていない。

判定は3代目に置き換えた: 「結果ページで繰り返していたトークンが **1種も消えて
いない** = ページが変わっていない」。入れ子の形にも行の同定にも依存しない。
この判定は「一部だけ消えたページ」(骨だけのおすすめカード等) を通しうるが、
その場合に出る値も不変条件 (行側 XOR 0件側) を満たし、常真の枠には決してならない
ことをテストで固定した。残存の内訳は成功時も診断として印字する。

### 回り方そのものを変えた (構造スナップショット)

ここまでの4欠陥はすべて「実画面の形を1つずつ、実行してから学ぶ」ことの帰結
だった。`observe-list` は読んだDOM構造 (タグ・クラス・親子のみ、13.2適合) を
丸ごと保存し、ログにも圧縮ブロックで埋め込むようにした。
`scout recon replay-list` が保存された構造に対して実行時と同一の解析を再実行する。

**これで経済が変わる。** 実行1回の価値は「値が出たか」ではなく「構造を持ち
帰れたか」になり、後者は失敗しない。以降のアルゴリズム修正は、実データへの
replay で確かめてから送れる。

### 3回目の実行を構造スナップショットで解剖した (2026-08-13 同日)

3回目の実行は前進した: 行は `div.c-search-member-card` (25個) と正しく同定され、
0件検索で消えることも確認された。しかし `nav.list_ready_selector` の0件表示側と
`nav.drawer_close_selectors` は UNRESOLVED のままだった。

今回はログから構造スナップショット (結果ページ4062節点 + 0件ページ2枚) を回収し、
**運用者に触れずに** 原因を確定できた。

**残った2つの失敗は同根だった。** 0件ページには結果テーブル領域が丸ごと無く、
ローダー (`div.c-loader-view` 系) が残留していた -- 0件表示が出たのではなく、
**XHR待ちのローダー画面を「構造が静止した」と誤認して撮影していた**。構造静止の
判定は数フレームの安定で満了するので、通信待ちの静けさを完了と読む。初回の
遷移だけはJS起動が遅く、偶然読み込み後に撮れていた。ドロワーも同じ理由で、
再遷移後のローダー画面から行を探して「行が現れない」まま諦めていた
(しかも報告は誤って「クリック領域が無い」と述べていた)。

カード内のクリック領域は実データ上ちゃんと存在する (`__main-content`、操作部品
なし、74節点) ことも、スナップショットから確認できた。

### 対処

1. **観測から導いた一時要素の消滅を待つ。** 「遷移直後には在り、読み込み完了後の
   結果ページには無い」トークン (= この実行自身のデータでローダー一式に一致) が
   全て消えるまで待ってから撮影する。語彙のハードコードではない。消えなければ
   その事実を `loader_cleared=false` として診断に残す
2. **コンテナ単独の値を最優先に。** 「結果ページに一意 / 全0件ページの読み込み後に
   存在 / 遷移直後には不在」の3条件が観測できたら、コンテナ1トークンを値にする。
   取得指針の理想形 (「行のコンテナを選ぶと空結果でも待てる」) がそのまま成立し、
   枠は「遷移直後から在る」ので3条件目で構造的に落ちる
3. **ドロワーを試せなかった理由を、推定ではなく実際の分岐から印字する。**
   「クリック領域が無い」という誤った報告は、理由の推定が原因だった

### この回の意味

運用者の往復を1回も使わずに、原因の確定・修正・実データへの再生検証まで済んだ。
スナップショットの狙いどおりである。

## 「この媒体に0件表示は無い」は誤りだった -- 一時要素の定義が観測を上書きした (2026-08-13)

### 何が起きたか

4回目の実測は、これまでで最良のデータを持ち帰った。にもかかわらず解析は
`nav.list_ready_selector: UNRESOLVED` を出した。スナップショットを開くと、
**0件表示の専用要素は実在した**: `div.c-not-found--searches` が0件ページ2種の
両方に在り、結果ページには無い。3回目の解剖で出した「この媒体の0件ページには
専用要素が存在しない (領域ごと消える)」という結論は、読み込み途中のキャプチャ
から引いた誤りだった。

実在する要素が UNRESOLVED になった原因は、こちらの2つのフィルタである。

1. **「遷移直後に在り、結果ページに無い」をローダーの定義にしていた。**
   SPA の描画は速く、age 変種は遷移直後の1枚の時点で0件表示を描画し終えていた。
   「結果ページに無い」は0件表示の定義そのものであって、ローダーである証拠では
   ない。この定義は0件表示を一時要素と誤分類し、「0件ページが完了していない」
   と判定し続けた。
2. **「遷移直後の1枚に在ったものは0件表示candidateから外す」も同じ誤りを含む。**
   読み込み骨組みを外すための守りが、先に描画し終えた本物まで外していた。

さらにコードレビューで同型の欠陥を2つ発見した (実行前に手元で):
検証0件ページが1枚も無いときに「すべての0件ページに在る」が空虚に真になり
読み込み後マーカーが全トークンに開く穴と、遷移直後の1枚が無いときに
「early に不在」が空虚に真になる穴。**「不在の観測」と「観測の不在」の混同**が、
合計4箇所に同じ形で入っていた。

### 対処

1. **一時要素 = 「同じ遷移の中で消えたことが観測された」もの** に定義を差し替えた
   (`transient_tokens`)。実測ではローダー一式11種が一致し、0件表示は残った。
2. 0件表示候補の除外は2体制にした (`empty_exclusions`)。その遷移でローダーが
   剥がれるのを観測できたページは、観測済み一時要素だけを除外する (遷移直後から
   在っても、剥がれた後に残ったものは0件描画の一部)。何も消えていないページは
   従来どおり保守的に全除外する。観測済み一時要素はどちらの体制でも除外する。
3. 空虚な真を2箇所とも塞いだ: 完了した0件ページ0枚 → マーカーを出さない、
   遷移直後の1枚が0枚 → マーカーを出さない。
4. ライブ側は、先行する遷移で消滅を観測したローダー語彙を後続の遷移に持ち回る
   (pagination 変種は遷移直後の1枚が起動前の骨組み26節点で、自分の語彙を導けず
   読み込み途中を撮影していた)。
5. 値の優先順を戻した: **行∨0件表示のペアが本命**、読み込み後マーカーはペアが
   組めない媒体のための控え。再生の結果、実データから
   `"div.c-search-member-card, div.c-not-found--searches"` が出た (0件側は
   2変種の両方で確認済み)。

### この回の意味

「無い」という結論は「観測できなかった」の言い換えであってはならない (原則3の
系)。読み込み途中のキャプチャから「専用要素が無い」と結論した時点で誤りは
始まっていた。今回も運用者の往復は使っていない -- 4回目のスナップショットへの
replay だけで、誤結論の発見・定義の差し替え・値の導出まで済んだ。

## 「押したが開かない」は嘘だった -- クリックは完了していなかった (2026-08-13)

### 何が起きたか

4回目の実測のドロワー報告は「div.c-search-member-card__main-content を押しましたが、
新しい要素の出現を検知できませんでした」だった。これを根拠に「押しても開かない」
問題として考察を進めていた。

スナップショットを見直すと `after_click` (クリック後の木) が保存されていなかった。
コード上、クリックが成功した経路では必ず保存される。つまり **クリックは例外で
中断されており、一度も完了していなかった**。例外パスが握り潰され、報告文は
「押しましたが」と印字していた -- 押せていない事実を「押したが無反応」に
すり替える、この開発が繰り返し潰してきた形の報告の嘘である。

結果ページの構造には、遮った可能性が高い犯人も写っていた: ツアー案内の吹き出し
`div.c-tour-guide__tooltip` と `div.c-overlay` (8個) が常駐している。Playwright は
クリック対象が別要素に覆われていると操作可能性の検査で満了する。

### 対処

1. **クリック未完了 (`drawer_click_failed`) を「押したが無反応」と別の事実として
   報告する。** 「押しましたが」と印字しないことをテストで固定した
2. **何が遮っていたかを DOM から直接読む** (`elementFromPoint`)。例外メッセージの
   推定ではなく、クリック地点に実際に居る要素と祖先の構造トークンを持ち帰る
   (タグ・クラスのみ、13.2)。ツアー系の語があれば実画面での解消手順まで印字する
3. **失敗時もクリック時点の木を保存する。** 保存が無いこと自体が今回の証拠に
   なったが、それは偶然であり、以後は失敗の瞬間も replay の材料にする
4. クリック前に Escape を1回送る (キー入力のみ。外向きの送信は起きない)。
   吹き出しは1枚目のカードに係留されがちなので、遮られたら2枚目で1度だけ再試行する

### この回の意味

「押したが開かない」と「押せていない」は、次の一手が全く違う (前者は媒体の作りの
問題、後者はこちらの操作の問題)。報告がこの区別を持たないと、持ち帰った実データが
あっても考察が誤導される。区別は例外の握り潰しをやめて事実を運ぶだけで手に入った。

## 遅れてマウントされる要素が0件表示を名乗った -- 2枚のXORは撮影後の変化に破られる (2026-08-14)

### 何が起きたか

5回目の実測で、解析はツアー案内 `div.c-tour-guide` を0件表示として **推奨した**
(`nav.list_ready_selector: "div.c-search-member-card, div.c-tour-guide"`)。
運用者が指示どおり貼っていれば、結果ページにも遅れて出るツアーUIが「0件表示が
出た」と読まれ、一覧の描画前に待機が成立する -- 原則2の静かなゼロ件が座標に
入るところだった (記入済みの正しい値を上書きする直前で止めた)。

原因は時間である。ツアー案内は結果ページの撮影時にはまだマウントされておらず、
0件ページの撮影時には在った。**settled 2枚のXOR不変条件を完璧に満たしていた** --
不変条件は撮影した木に対してしか成立せず、撮影後にマウントされる要素を見ない。
実際にはクリック後の木 (再遷移した結果ページ) に行25枚とツアーが同居して写って
おり、「ツアーは0件表示ではない」証拠はこの実行自身のデータの中にあった。

同じ実行でもう1つ: pagination 変種の遷移直後の1枚には、直前の age 変種の
0件表示が **残像として** 写り込み、新ページの描画で消えていた。「同じ遷移の中で
消えた = 一時要素」の定義がこれを拾い、本物の `div.c-not-found` を全域で
ローダー扱いする経路があった。

### 対処 (反証レビューの確定3件を含む)

修正を送る前に敵対的レビュー (4視点で探索 → 各指摘を最小再現で検証) にかけ、
12指摘中3件が確定した。うち1件は最初の修正案自体の欠陥である。

1. **行が1枚でも見えている観測ページを全部「結果側」に合流させる**
   (`rows_present_union`)。0件表示を名乗る資格は「結果 settled に不在」ではなく
   「行が見えているすべての観測 (結果 settled / 遷移直後 / クリック後 /
   差し戻されて一覧が出たままの0件ページ) に不在」。行が見えないページは
   合流させない -- そこには本物の0件表示が写り込むことがある。
2. **[レビュー critical] ライブの報告もクリック後の木を含む最終形で解析し直す。**
   最初の修正は解析がクリック前に1回走るライブ経路で構造的に届かず、
   「実行時と再生が同一解析を通る」保証が入力の非対称で破れていた。
   運用者が貼るのはライブ報告なので、これを直さない限り毒は残っていた。
3. **[レビュー major] 消滅語彙を用途で2系統に分けた。** 残像 (前ページの内容) と
   前ページから残留したままのローダーは件数の列から区別できないことがある。
   候補除外は残像ガード **無し** (`vanished_tokens`) -- 取りこぼすと値に毒が入る
   (レビューが settled ローダー残留 + 差し戻しの組で実際に再現)。完了判定と
   ライブの待機は残像ガード **付き** (`transient_tokens`) -- 残像を学ぶと後続の
   遷移で本物の0件表示の消滅を待って満了する。区別できないときに、どちらへ
   倒すかを用途で決める。
4. **[レビュー minor] ツアーの閉じ試行の失敗を報告から落とさない**
   (2回目の `_dismiss_tour` の False を捨てない)。
5. ツアーはクリックを遮ることも確定した (覆い要素の直接観測)。偵察が自分で閉じる
   (`_dismiss_tour`): ツアー領域内の a/button のうち文言が閉じる/スキップ系の
   ものだけを押す。class に scout を含む要素は文言に関係なく押さない (ツアーは
   スカウトボタンに係留されているため, 13.6)。

修正後の replay: 4回目は従来どおりペア `"div.c-search-member-card, div.c-not-found"`
を出す。5回目は (c-not-found が残像として消えた証拠を持つため) ペアを出さず、
読み込み後マーカー `div.c-search-conditions` を出す -- 4回目が別案として挙げていた
のと同じ値で、記入済みの座標と両立する。**どの経路からも毒された値は出ない。**

### この回の意味

スナップショットは実行の丸ごとではなく **撮影時刻の断面** である。断面同士の
差分に立てた不変条件は、断面の間に起きる変化 (遅延マウント・SPA遷移の残像) に
破られる。防ぎ方は断面を増やすことではなく、**同じ実行が既に持っている他の断面を
証拠として合流させる** ことだった。そして「観測から区別できないもの」に出会ったら、
推測で埋めるのではなく **どちらへ倒すと失敗が見えるか** で設計を決める。
今回も運用者の追加往復はゼロである。

## ツアーは「閉じる」ものではなく「終わらせる」ものだった (2026-08-14, 実測6回目)

### 何が起きたか

6回目の実測で、`nav.list_ready_selector` はライブの報告でも記入済みの座標と
整合する値を出した (5回目で入れた解析修正が実データで機能した)。一方、ツアーの
自動閉じは失敗し、報告は正直に「閉じる/スキップの文言を持つ部品が見つからない」と
述べた。

運用者が Actions のアーティファクト (構造スナップショット) を直接提供してくれた
ので、ツアーの吹き出しの中身を初めて完全に観測できた: 見出し + 本文 + ボタン枠に
**汎用の button.c-button が1つだけ**。「閉じる」「スキップ」に相当する部品は
存在しない。つまりこのツアーは「次へ」で進めて最後まで到達させる型で、文言ヒント
での閉じは構造的に不可能だった。ツアー本体の外に同じ吹き出しの隠しテンプレートが
常駐していることも分かった (探索範囲を広げるとそれを押そうとして満了する)。

### 対処

`_dismiss_tour` を3段の梯子にした。(1) 文言ヒント (画面が変わって閉じる部品が
現れたら1手で済む)、(2) **進めて終わらせる** -- 吹き出しの最後のボタンを押し
続ける (上限10回。段が進むと吹き出しは作り直されるので毎回引き直す)、(3) 背景
オーバーレイを1度だけ押す。どの段も探索はマウントされた div.c-tour-guide の中
だけに限定し (隠しテンプレート対策)、class に scout を含む要素は文言に関係なく
押さない (13.6)。押しても消えないツアーで無限ループしないこと・scout 係留の
実体が最後のボタンに来ても押さないことをスタブページのテストで固定した。

### この回の意味

「閉じられない」の原因は語彙不足ではなく **型の誤認** だった。ツアーUIには
「閉じる型」と「完走させる型」があり、後者に閉じる語彙をいくら足しても届かない。
スナップショットが吹き出しの中身 (ボタンが1つ・文言部品なし) を持ち帰ったから、
語彙を足す無駄な1往復をせずに型ごと切り替えられた。

## 読み込まれなかった0件ページが、読み込まれた方を全否定した (2026-08-14, 実測7回目)

### 何が起きたか

7回目で `nav.list_ready_selector` が UNRESOLVED に戻った (6回目では正しい値を
出していた)。ツアーの自動閉じが機能してカードのクリックは初めて完了したが、
その傍らで list_ready が回帰していた。

スナップショットで原因が確定した。**pagination 変種が26節点の起動前スケルトンの
まま撮影された** (age 変種は2371節点で正常に0件表示を描画)。26節点のページは
サイトの共通要素をほとんど持たない -- 0件を返したのではなく、そもそも読み込まれて
いなかった (別URLへ転送された可能性。landed_url が違っていた)。

にもかかわらず、このスケルトンは「使える0件ページ」と誤判定された。使用可否は
「結果ページで繰り返していた要素が1つも消えていないか」で見るが、**読み込まれて
いないページは繰り返しも全滅する** (51種消滅)。そして `ready_values` は
「0件表示は使用可能な全0件ページに存在」を不変条件に課すので、age が正しく
見つけた `div.c-not-found` を、それを持たないスケルトンが全否定して値を消した。

### 対処

`ZeroPage` に `chrome_overlap` (結果ページの **非繰り返し** トークン = サイトの
什器のうち、このページにも在る割合) を追加し、`zero_page_is_usable` に
「共通要素をほとんど含まないページは読み込まれていない」ゲートを足した。
実測で実ページ0.77・スケルトン0.05と桁で違うので、閾値0.15は鋭敏でない。
弾いた理由 (残存率つき) は診断に印字する。

これで7回目のスケルトンは弾かれ、age 側から正しい値が出る (1変種のみの注記付き。
それも honest -- この実行では実際に1変種しか描画されなかった)。6回目の値は
不変。回帰テストは変異バッテリーに「片方が非ロード」の形を追加して固定した。

### この回の意味

「繰り返しが全滅した」には2つの意味がある -- **0件だった** と **読み込まれて
いない**。件数だけでは区別できない。サイトの什器 (どのページにもある共通要素) が
残っているかを見れば区別できる。0件ページは什器を保つが、起動前のスケルトンは
保たない。ここでも「観測から区別できないもの」を推測で埋めず、区別できる別の
観測量 (什器の残存) を足して解いた。

## 遮断を早く武装しすぎて、押す対象そのものを消した (2026-08-14, capture-open 1回目)

### 何が起きたか

段階3の `capture-open` の初回実行が、**サイトのロゴ** (`a.c-logo__image`) を押した。
カードの中ですらない。

原因は武装の位置である。「押してよいか分からないボタンを押すのだから、何よりも
先に武装する」という設計にしていた。安全側ではある (実際、送信は1件も起きて
いない) が、**一覧のデータ読み込みも非GETである**。武装したまま遷移したので
データ読み込みごと遮断され、カードが1枚も描画されなかった。

そして探索は止まらなかった。行の同定を「最も繰り返している構造」に任せていた
ため、カードの無い画面ではヘッダの繰り返しが勝ち、その中の押せる要素として
ロゴが選ばれた。**押す対象が存在しない画面で、押す対象を探し当ててしまった。**

### 対処

1. **武装の位置を変えた。** 遮断は仕掛けるが武装せずにページを開き、一覧が
   描画されるのを待ってから、**押す直前に武装する**。探索の間はずっと武装した
   ままで、`finally` で解除する。「押す前に武装」という不変条件は保ったまま、
   「描画を殺さない」を両立させた
2. **描画されたことを確定済みの座標で確かめる。** `nav.list_ready_selector` の
   行トークンが実際に現れるまで進まない。現れなければ押さずに報告する
3. **行は座標の行トークンで選ぶ。** 「最も繰り返している構造」は、描画に失敗した
   画面ではヘッダを指す。7回かけて確定させた座標があるのだから、それを使う
4. **押した後の再遷移をやめた。** 武装中は再遷移しても一覧が戻らない (同じ理由)。
   代わりに開いた領域を閉じてから次へ進み、URLが変わったら **そこで打ち切る** --
   武装したまま知らない画面を押し進めない

### この回の意味

安全側の設計が、観測を成立させなくすることがある。「遮断は早ければ早いほど
安全」は正しいが、**遮断したものの中に、観測の前提そのものが入っていた**。
安全と観測は両立できる -- ただし「いつ武装するか」を1箇所に絞り、その1箇所を
テストで固定する必要がある (`test_every_click_happens_while_the_gate_is_armed`)。

もう1つ: **止まるべきときに止まらない探索は、無意味な観測を作る。** 押す対象が
無いなら押さない、という判断を入れていなかったので、代わりのものを押した。

## 確定した座標があるのに、推定を経由して行を取り逃した (2026-08-14, capture-open 2回目)

### 何が起きたか

一覧は正しく描画され、`nav.list_ready_selector` による確認も通った。にもかかわらず
「行が取れない」で止まった。しかも報告は **「遮断を武装できなかったため」** と
述べた -- 武装は行を取った後に行うので、これは嘘である。本当の理由 (行を取れ
なかった) は補足行にしか出ていなかった。

欠陥は2つ。

1. **行の取得に繰り返し構造の解析 (`row_group_candidates`) を経由していた。**
   あれは極大性の規則で「外側の繰り返しに含まれる群」を落とす。カードが別の
   繰り返し構造 (行を包む枠) の内側にあると、カードの群が消える -- observe-list
   の実測2回目で行が `div.c-segment` に化けたのと **同じ規則** である。
   7回かけて確定させた座標が手元にあるのに、わざわざ推定を経由していた。
2. **報告の検査順が時系列と逆だった。** 武装の検査を行の検査より前に置いたので、
   行の段階で止まった実行に「武装できなかった」という誤った理由が付いた。

### 対処

1. 行は `indices_with_token(tree, row_token)` で **直接指す**。確定した座標が
   あるなら、推定を経由しない。
2. 報告の検査を時系列の順に並べ替えた (木 → 行 → 武装)。

### この回の意味

**確定した知識を、確定していなかった頃の仕組みで扱っていた。** 座標は「実行時に
使うもの」であると同時に「探索の足場」でもある。段階を1つ上がったら、下の段で
使っていた推定を外せるかを見直す必要がある。

報告の側も同じ形の誤りを繰り返した (実測4回目の「押しましたが」と同型)。
**検査の順序は、出来事の順序と一致させる。** 一致していないと、途中で止まった
実行に、まだ起きていない工程の失敗が理由として付く。

## 報告が事実と食い違う誤りを、構造で二度と起こせなくする (2026-08-14)

### 何が起きていたか

運用者から「今後絶対に嘘をつかないように」と指示があった。**報告が実際の実行と
食い違う**という同じ形の誤りを3度繰り返していた:

- 実測4回目: クリックが**完了していない**のに「押しましたが新出要素なし」
- capture-open 1回目: 描画されていない画面で押したのに理由を取り違えた
- capture-open 2回目: **行を取れなかった**実行に「遮断を武装できなかった」

共通の原因は同一である。**報告が独立したブール値を手で並べた順に検査していた。**
順序を1つ間違えるか、ブール値が実行と食い違って立つと、途中で止まった実行に
「まだ起きていない工程の失敗」が理由として付く。個別に直しても、次の報告分岐で
再発する形だった。

### 構造的な対処 (`recon/capture_open.py`)

報告が推測する余地を無くす。工程を**時系列で1本の鎖**にし、各工程に「そこを
通過した証拠となるブール値」を持たせる。実際に到達した地点は「鎖の中で最初に
False になる工程」ちょうど1つに決まる -- 後の工程は前を通らないと始まらないから。
報告 (`render`) はこの1つの値 (`OpenObservation.reached()`) だけを見る。順序は
この1箇所に閉じ込め、テストで固定した。

さらに、**単調性を破る状態は握り潰さず例外にする。** 後の工程の証拠が True なのに
前の工程が False なら、実行のどこかがブール値を事実と違えて立てている。その状態で
報告を出せば必ず嘘になるので、報告せず停止する。「もっともらしい嘘」より「見える
停止」を選ぶ (原則2の精神)。

テスト (`test_capture_open.py`) で3点を固定した:
1. 各停止地点は自分の理由だけを出し、**後の工程の理由を語らない**
2. 行で止まった実行は武装を理由にしない (実測2回目そのもの)
3. 単調性を破る状態は render を拒否して例外にする

### この原則

**検査の順序は、出来事の順序と一致させる。** そして「今どこまで進んだか」は
1つの値に集約し、報告はその値だけを見る。ブール値の組み合わせから報告が理由を
推測する設計は、いつか順序を間違える。同じ設計を他の報告 (observe_list 等) にも
広げる価値がある -- ただし今回はまず、直近で嘘をついた capture_open に入れた。

## 「閉じられない」は打ち切る理由ではなかった -- 導線の1歩目で止まっていた (2026-08-14, capture-open 3回目)

### 何が観測できたか

3回目で初めて工程を最後まで通った (一覧の描画・行の取得・武装、すべて通過)。
そして **送信路への導線が見えた**:

カードのチェックボックス (`label.c-checkbox--blue`) を押すと、一括スカウト用の
バー `div.c-sticky-scout-bar` が現れ、その中に `button.c-sticky-scout-bar__scout-button`
がある。ドロワーではなく **選択 → 一括送信** の作りだった。非GETは1件も発生して
いない (選択そのものは通信しない)。

### 3つの欠陥

1. **探索が導線の1歩目で止まった。** 「増えた領域を閉じられなければ打ち切る」と
   していたため。しかし閉じられなかったのはバグではなく **閉じるものではなかった
   から** である -- 選択バーはモーダルではない。現れたものを辿らない限り送信画面へは
   到達しないのに、辿る前に止める設計になっていた。
2. **報告が「ドロワーは開きました」と述べた。** 観測したのは「構造が17種増えた」
   であって、それがドロワーかは分かっていない。増えたのは選択バーだった。
3. **クリックが完了しなかったのに画面が変化した事実を、片方しか報告しなかった。**
   押下は伝わり、その直後の安定性検査で満了した可能性が高い。「押せなかった」だけ
   だと変化を、「押せた」だけだと完了しなかった事実を握り潰す。

### 対処

1. `revealed_controls` (純粋): 押した結果現れた領域 **の中だけ** からコントロールを
   拾い、次の候補として待ち行列に積む。探索は導線を辿る。打ち切るのは別画面へ
   遷移したときだけ (武装したまま知らない画面を押し進めない)。同じものは二度
   押さない。上限は8回
2. 未確認の領域を「ドロワー」と呼ばない。「新しい構造は現れたが、閉じられる領域か
   は確認できていない」と述べ、現れた構造を並べる
3. クリック未完了と画面変化を **両方** 述べる

### この回の意味

**停止条件が観測の前提を切っていた。** 「閉じられたか」は健全性の確認であって、
探索を続ける条件ではない。確認できないことを進行不能の理由にすると、確認できない
形の画面 (今回は選択バー) の先へ永久に進めない。停止条件は「危険なとき」
(別画面への遷移) に絞り、それ以外は観測を続けて事実を持ち帰る。

## 8個すべてクリックが完了せず、理由を1つも残していなかった (2026-08-18, capture-open 4回目)

### 何が起きたか

導線を辿る修正が入り、探索は8個の候補を試した。**その8個すべてが
「クリックは完了しませんでした」だった。** しかも1個目では画面の構造が17種
増えている -- 押下自体は伝わっていた。

原因はほぼ確実に、1個目の押下で現れた **画面下部に固定表示される一括操作バー**
(``div.c-sticky-scout-bar``) である。Playwright の ``click`` は「見えて・動かず・
有効で・イベントを受け取れる」まで待つ。固定バーが対象を覆うか、出現の
アニメーションで要素が動き続けると、この検査は満了し続ける。

**より悪いのは、理由を1つも残していなかったことである。** ``except Exception:
pass`` で握り潰していたので、報告は8行すべて「完了しませんでした」としか言えず、
何が起きているのか運用者にも開発側にも分からなかった。**失敗の理由は観測であり、
捨ててはいけない。** これは実測4回目の「押しましたが」と同じ形の誤り
(事実を落とす) の、別の現れ方だった。

### 対処

1. **理由を分類して必ず報告する** (`click_failure_kind`、純粋)。覆われている /
   動き続けている / 見えない / 無効 / 複数一致 / 満了、の定型句に落とす。
   **生の例外メッセージは決して出さない** -- Playwright のメッセージには要素の
   outerHTML (= ページの文言) が混ざる (13.2)。
2. **押下を届ける経路を用意する。** 通常のクリックが満了したら
   ``dispatch_event("click")`` で DOM イベントを直接発火する。操作可能性の検査を
   経ないので、固定バーに覆われていても届く。
   安全性: 押す対象の選定は変わらない (カードの中、または直前に現れた領域の中に
   限定済み)。そして遮断は武装したままなので送信は物理的に起こらない。
   **「押せない」で観測を諦めるより、届く経路を用意して事実を持ち帰る。**
3. 報告に「理由 / 押下が届いたか」を出す。上限を8→14に上げた -- 送信を名乗る
   部品は安全のため後ろに回すので、上限が低いと到達しない。

### この回の意味

**握り潰した例外は、観測の穴である。** ここでは8回分の観測が「完了しなかった」
という1ビットに潰れていた。分類は1行で書けたし、その1行があれば次の手
(押下を届ける経路) が即座に決まった。例外を捨てる場所は、いつか必ず
「何が起きたか分からない」に変わる。

## 目印を1文字も書かない実行が、「送信画面まで到達していない」と説明していた (2026-08-18, 実行前に発見)

### 何が起きたか

実測5回目を待つ間にコードを読み直して見つけた。**実行前なので実害は出ていない。**

`capture-open` の報告は、`api.send.paid.url_pattern` を確定できなかったとき、
こう書くようになっていた。

```
api.send.paid.url_pattern: UNRESOLVED
  # 目印を運ぶ非GETはありませんでした (送信画面まで到達していない)。
```

入っているか」を照合するだけだった。書いていないのだから、載っているはずがない。

つまりこの説明は成立しえない条件を理由にしていた。もし実測5回目でスカウト
ボタンに到達し、送信APIが実際に叩かれて遮断されていたら、報告は **そのすぐ上に
遮断済みのPOSTを並べながら「送信画面まで到達していない」と書く。** 事実と正面から
矛盾する報告になる。

### なぜ起きたか

`capture-open` は `capture-send` の部品 (`sentinel`, `_drain` の照合) を借りて
作られた。借りた側は目印を書く工程を持っていないのに、**報告の文面だけが「書いた
前提」のまま残った。** 借用は状態を運ばないが、文面は前提を運ぶ。

### 対処

1. **書けるなら書く。** 押す直前、**直前に現れた領域の中の** 入力欄に目印を
   書き込む (`revealed_text_fields`、純粋 + `_write_sentinel`)。書き込みは送信
   ではないし、書いた内容を保存しようとする通信があってもそれは非GETなので
   遮断されている。書かなければ、遮断した複数の非GETから送信路を選ぶ根拠は
   永久に手に入らない。
   探索範囲を現れた領域に限るのは `revealed_controls` と同じ理由 -- 画面全体に
   書くと常駐の検索欄まで書き換えて、一覧そのものが変わる。
2. **書けなかった実行は、書けなかったと言う。** 目印が無いときの理由を
   「到達していない」(観測していない) から「目印を書けていないので、どれが
   送信路かを決められない」(観測した事実) に直した。値は UNRESOLVED のまま、
   候補は候補として並べる (原則3)。
3. 押下ごとの行にも「目印を書き込めたか」を出す。

### この回の意味

**部品を借りると、その部品が前提にしている工程まで借りたつもりになる。**
ここでは「目印を書く」という工程が抜けたまま、目印を照合するコードと、目印が
あることを前提にした文面だけが移ってきた。借りた側で成立しない条件を理由に
書いた報告は、条件が偶然そろわない限り必ず嘘になる。

**そして、成立しえない分岐はテストでは落ちない。** `carried_sentinel` が真に
なりようがないので、嘘を書く側の分岐だけが常に通る。テストは「起こりうること」を
固定するので、**起こりえないことを前提にした文面は素通りする。** 報告の文面は、
それを書く条件が実際に起こりうるかを別途確かめる必要がある。

## 「非GETを全部止める」ままでは段階3が原理的に終われなかった (2026-08-18, capture-open 5回目)

### 何が起きたか

探索は3個の候補を試し、**送信路の1歩手前まで見えた**。

1. カードのチェックボックス → 一括スカウトバーが出現 (18種増加、
   `button.c-sticky-scout-bar__scout-button` を含む)
2. `input.c-checkbox__input` (ラベルの陰の実体) → 見えないので押下を直接届けた
3. カードの `button.c-button.u-wd-100p.c-button--small` → **`/customers/network_error/`
   へ画面ごと飛ばされ、探索は打ち切り**

3で遮断された非GETに答えがあった。

```
POST /api/customers/graphql/MemberOnScoutProfileModalOfDesktop
POST /api/customers/members/mark_read/
```

**媒体は GraphQL の単一ページアプリだった。** 候補者プロフィールのモーダルは、
名前のとおり GraphQL の読み取りで中身を取ってから描画される。つまり
**画面を開くための読み取りが POST で来る。**

遮断は fail-closed で「GET/HEAD 以外は全部止める」。だからこの読み取りも止まる。
止まるとモーダルは中身を得られず、媒体の共通エラー処理が働いて画面ごと
エラーページへ飛ぶ。

**これは調整で直る不具合ではなく、前提の破綻である。** 送信画面へ到達するには
読み取りを通す必要があり、読み取りは POST で来る。「非GETを全部止める」ままでは、
何回実行しても段階3は終わらない。

### 対処

**通す条件を「メソッド」から「操作の種類」へ移した。** GraphQL では読み取りは
`query`、状態変更は `mutation` であると **仕様で決まっている**。スカウト送信は
状態変更なので `mutation` である。

1. `recon/graphql.py` (純粋): `is_read_only_graphql(url, body)`。
   **判定できないものは全て「通さない」に倒れる** -- 本文が読めない、JSONでない、
   `query` フィールドが無い、URLが GraphQL のエンドポイントに見えない、
   まとめ送りに1つでも `mutation` が混ざる、いずれも通さない。
2. `GateMode` を導入。**既定は `BLOCK_ALL` (従来どおり)** で、緩和は
   `BLOCK_WRITES` を名前で明示したときだけ効く。使うのは探索コマンド
   (`capture-open`) だけ。送信路が判明した後の `capture-send` は従来のままである。
3. **止め方を「中断」から「空の応答」へ変えた** (`RECORD_AND_STUB`)。中断は媒体
   から見ると通信障害なので共通エラー処理が働く。空の応答なら画面が残り、探索を
   続けられる。**リクエストがサーバへ到達しない点は中断と同じ** である。
4. 報告に **通した読み取りを出す**。緩和が黙って効いていると、運用者は何が
   守られているのか確かめられない。

### 残るリスクを隠さない

媒体が送信を GraphQL の `query` として実装していれば、この判定は通してしまう。
GraphQL のクライアントもサーバも通常そうは作らないが、可能性はゼロではない。
**緩和の範囲を仕様上の区別1点に限定し、既定を従来のままにし、緩和が効いた実行では
報告にそう書く** ことで、この判断が黙って広がらないようにしてある。

### この回の意味

**fail-closed は「何を止めるか」ではなく「何を安全と確実に言えるか」で引く線である。**
最初の線 (メソッド) は、媒体が読み取りに POST を使う世界では引く場所が間違って
いた。線を引き直すときに問うべきは「通したいか」ではなく「通すものが安全だと
何を根拠に言えるか」であり、ここでは GraphQL の仕様がその根拠を与えた。
根拠の無い緩和は、どれだけ小さくても入れてはいけない。

## 読み込み表示を「現れた領域」と誤認し、body を領域にしてページ中を押した (2026-08-18, capture-open 6回目)

### 何が起きたか

遮断の線を引き直した結果、**送信フォームまで開いた**。通した読み取りがそれを
証明している。

```
graphql/MemberOnScoutProfileModalOfDesktop   候補者プロフィールのモーダル
graphql/GetScoutSideCoverInfo                スカウトのサイドカバー (ドロワー)
graphql/JobOfferSearchOnScoutMessageForm ×3  **スカウト送信メッセージフォーム**
```

それなのに座標は1つも埋まらなかった。目印を書き込める入力欄が「現れた領域」に
無かったからである。**現れた領域の測り方が2箇所で壊れていた。**

#### 1. 読み込み表示を測っていた

報告の「増えた構造」は ``div.c-loader`` 一色だった。媒体は押下のあと読み込み
表示を出し、GraphQL で中身を取ってから差し替える。

**読み込み表示が出ている間、DOM の構造は静止している。** 要素数は変わらないので
`wait_for_structure_to_settle` は「落ち着いた」と答える。その瞬間に測れば、押して
現れたものは読み込み表示そのものになる。**構造だけを見ていては、この2つを
区別できない。**

#### 2. body を領域の根にしていた

スカウトのサイドカバーが開いたとき、増えたトークンに
``body.c-body--fixed-by-sidecover`` が含まれていた。body の部分木は **ページ全体**
である。そこを「現れた領域」として探索したので、画面中のボタンを片端から押す
ことになった。実際、4個目以降は無関係なボタンが並び、最後は検索画面へ遷移して
探索が終わった。

### 対処

1. **中身が届いてから測る** (`wait_for_content_to_arrive`)。1度落ち着くのを待ち、
   **通信の静止を待ち**、もう1度落ち着くのを待つ。構造の静止だけでは足りない
   場面がここだと分かったので、ここでだけ通信を併用する。待てなくても失敗に
   しない (待ちは精度のためのもので、後段は測れる)。
2. **領域の根から「ページそのもの」を外す** (`region_roots`、純粋)。
   `html` / `body` と、木の半分以上を占める部分木は領域ではない。
   「ほとんど全部を含むもの」は **ページの状態が変わったことの目印** であって、
   押しに行く先ではない。
   割合の規則は木が十分大きいときだけ適用する -- 数個の要素しか無い画面で
   「半分以上」と言っても何も言っておらず、正当な領域を捨てるだけである。
3. ツアー案内は領域から外す。閉じる対象であって、ドロワーでも送信フォームでもない。
4. 報告の「増えた構造」を6件から14件に増やす。クラス名は構造でありページの文言
   ではない (13.2)。6件で切ったせいで、読み込み表示だけが並び **その後ろに何が
   現れたのかが報告から落ちていた**。

### この回の意味

**「落ち着いた」は「終わった」ではない。** 読み込み表示は、変化が止まっている
のに処理は終わっていない状態そのものである。静止を完了の代理指標にすると、
必ずこの一点で取り違える。指標を選ぶときは「測りたいことと一致しない場合が
あるか」を先に問う必要がある。

**そしてもう一つ。「増えたもの」は必ずしも「現れた領域」ではない。** body に
クラスが1つ付くのも「増えた」である。差分は事実だが、その事実が何を指している
かは別の判断であり、そこを飛ばすと差分の広さのぶんだけ探索が暴れる。

## 戦略の見直し: 押しに行かず、配信ファイルを読む (2026-08-18, 運用者の問いかけを受けて)

### 問い

運用者から「同じ行動を何度も繰り返している気がする。この計画は完璧か」と問われた。
記録を確かめると足踏みはしていなかった -- 毎回さらに奥へ進んでいる。

| 実行 | 到達点 |
|---|---|
| 1回目 | カードのボタンを押せず、サイトのロゴを押した |
| 2回目 | 行が取れない / 報告の順序が逆 |
| 3回目 | 一括スカウトバーを発見 |
| 4回目 | 押下が届くようになった |
| 5回目 | 媒体が GraphQL SPA だと判明 |
| 6回目 | **スカウト送信フォームまで開いた** |

しかし問いの本質は正しかった。**この道は「生きたSPAと格闘する道」であり、UIの癖が
1つ現れるたびに実行を1回消費する。** ツアー案内、読み込み表示、固定バー、
サイドカバー。そして6回目の観測には ``button.c-button--disabled`` が出ていた --
送信ボタンは求人を選ぶまで押せない作りの可能性が高く、あと数往復が見えていた。

### 気づいたこと

**その往復は必要ではなかった。**

送信APIのURLの形は5回目・6回目で既に分かっている
(``/api/customers/graphql/<操作名>``)。足りないのは **送信 mutation の名前と
変数の形だけ** で、それは媒体が配信している JavaScript の中に文字列として
入っている -- GraphQL のクライアントは操作をどこかに持っていなければ送れない。

そして配信ファイルの取得は **GET** である。副作用が無い。つまりこの道では
**送信は「遮断したから起きない」のではなく、起こす操作そのものが存在しない**。

### 対処

`recon read-bundle` を追加した (`recon/bundle.py` が純粋な解析、
`recon/read_bundle.py` がGETだけのブラウザ側)。

- 認証済みセッションで一覧HTMLを GET し、``<script src>`` を集めて各ファイルを GET
- 素の GraphQL 文から操作の **種別・名前・変数の型だけ** を取り出す。原文は
  決して印字しない (13.2)
- 送信候補は「**mutation であり、かつ名前が送信を名乗る**」の両方を満たすもの。
  片方だけでは足りない -- 読み取りの名前にも ``Scout`` は入る
  (``MemberOnScoutProfileModalOfDesktop``)、既読更新のような無関係な mutation もある
- **1つに絞れなければ埋めない** (原則3)。候補は候補として並べる
- 上限で読まなかったファイル数を報告に出す (**静かな取りこぼしを作らない**)
- 素の GraphQL 文が残っていない作り (persisted query) の可能性も報告に述べる

`capture-open` は消さない。**最後の答え合わせ** -- バンドルから得た操作名が本当に
送信路かを、遮断を武装した1回の押下で確かめる -- に格下げする。

### この回の意味

**仕様どおりの方法が、最短の方法とは限らない。** 3章は「送信ボタンを押す直前に
遮断を武装する」と定めており、それは正しい。しかしそれは *押す必要がある場合の*
正しさである。押さずに同じことが分かるなら、押す仕組みの完成度を上げることに
往復を使うのは、目的ではなく手段に投資していることになる。

**運用者の「同じことを繰り返していないか」という問いは、進捗の問いではなく
手段と目的の問いだった。** 前進しているかだけを答えていたら、この道は見つから
なかった。

## 選択肢に足してステップを足し忘れ、何も実行せずに「成功」した (2026-08-18, read-bundle 初回)

### 何が起きたか

`read-bundle` を作り、CLI に配線し、`Recon (manual)` の選択肢にも足した。
**ワークフローのステップだけ足し忘れた。**

運用者が `read-bundle` を選んで実行した結果:

* 条件に一致するステップが1つも無い
* Playwright の導入まで済んで、そのまま後片付けへ
* **ジョブは「成功」と表示された**

報告は1行も出ていない。運用者は「出力が折りたたまれているのだろう」と受け取り、
ログを貼ってくれた。往復を1つまるごと無駄にした。

### なぜ悪いか

**これは 原則2 の「静かなゼロ件」そのものである。** 失敗より悪い。失敗すれば
運用者は何かがおかしいと気づくが、成功と表示されれば「実行したのに何も出ない」
と受け取り、媒体側やセッションを疑い始める。**間違った場所を探させる。**

そしてレビューでは見つからない。選択肢とステップは同じファイルの離れた場所に
あり、片方だけ足しても YAML としては正しいままである。CI も緑のままだった。

### 対処

1. ステップを足した (本来の修正)。
2. **機械で押さえた** (`tests/guardrails/test_workflow_safety.py`):
   * 選択肢に在る command は、必ずどれかのステップの条件に現れること
   * 逆に、選択肢に無い command を条件にしたステップが残っていないこと
     (選択肢から消しただけの死んだ設定は、次に読む人を誤らせる)

   この2本があれば、同じ足し忘れは **PR の時点で落ちる** -- 運用者の実行を
   1回消費してから気づく形にはもうならない。

追加したテストが本当に欠落を捕まえるかは、ステップを取り除いた木で確かめた
(捕まえた)。**空振りするテストを足さない。**

### この回の意味

**「成功」は「何かをした」を意味しない。** 条件分岐でステップを選ぶ作りでは、
どの条件にも一致しない実行が最も静かに成功する。分岐を足す仕組みには、
**必ず「どれにも当たらなかった」を失敗にする仕掛けを同時に入れる** 必要がある。

そして今回それを踏んだのは、直前に「静かなゼロ件」を何度も書いていた本人である。
原則を知っていることと、原則が破れる場所に気づくことは別である。だから機械で
押さえる。

## 素のHTMLの script タグしか見ず、「バンドルに無い」と述べた (2026-08-18, read-bundle 初回)

### 何が起きたか

```
script: 2 個中 2 個を読みました
見つかった操作: 0 個 (うち mutation 0 個)

api.send.paid.url_pattern: UNRESOLVED
  # 素の GraphQL 文がバンドルに残っていない作り
  # (persisted query / 事前コンパイル) の可能性があります。
```

**script が2個しか無いはずがない。** 媒体は単一ページアプリで、本体のコードは
必ず多数のファイルに分かれている。

原因は読み方だった。`context.request.get()` で **素のHTMLを取り、その中の
`<script src>` だけ** を集めていた。単一ページアプリの本体は入口の1本が動的に
読み込むので、**URLは HTML のどこにも書かれていない**。読み込ませない限り
存在が見えない。

さらに遮断が BLOCK_ALL のままだったので、仮にページを開いても画面は描画されず、
動的な読み込みも起きなかった (capture-open 5回目と同じ理由)。

### より悪いのは、読んでいない場所について述べたこと

報告は「persisted query の可能性があります」と述べた。**2個しか読んでいない
実行には、その資格が無い。** これは媒体の作りについての推測であり、運用者を
「媒体がそういう作りなのだろう」という誤った方向へ誘導する。実際の原因は
こちら側にあった。

### 対処

1. **ブラウザに実際に読み込ませて、飛んだ .js を数える** (`_scripts_the_browser_loaded`)。
   押下は0回のまま。素のHTMLの走査結果と合併する。
2. 遮断を BLOCK_WRITES にする。画面が描画されないと動的な読み込みが起きない。
   押下0回なので、送信は起こす操作そのものが存在しない。
3. **読めた数が少なすぎるときは、結論より先にそう言う** (`MIN_PLAUSIBLE_SCRIPTS`)。
   「無かった」ではなく「読めていない」と述べ、persisted query の話はしない。
4. 十分読んだうえで無かった場合も、押下0回のコマンドの視野の限界
   (ドロワーを開いたときにだけ読み込まれる部品は見えない) を併記し、
   **どちらかはこの観測だけでは決まらない** と述べる。

### この回の意味

**「探して無かった」は、探した範囲の広さとセットでなければ意味を持たない。**
範囲を報告しない「無かった」は、読み手には「存在しない」に見える。ここでは
範囲が2個だったのに、結論だけが媒体の作りの話として提示された。

観測の報告には常に「どこまで見たか」が要る。それが無い報告は、狭く見た結果を
広い主張に化けさせる。

## 「落ち着くまで待つ」を足したのに、まだ読み込み表示を測っていた (2026-08-18, capture-open 7回目)

### 何が起きたか

6回目の対処として `wait_for_content_to_arrive` (落ち着く → 通信が止まる →
もう一度落ち着く) を入れた。実行時間は1分から3分へ伸びた -- **待ってはいた。**
それでも「増えた構造」は変わらなかった。

### なぜ効かなかったか

対処に使った2つの指標が、どちらもこの場面では役に立たなかった。

* **構造の静止** -- 読み込み表示が出ている間、要素数は変わらない。「落ち着いた」と
  即座に答える
* **通信の静止** -- 満了していた (実行時間が伸びたのはこれである)。計測ビーコンや
  常時接続があると、通信は永久に静止しない

つまり待ちは **2つとも空振りしていた**。時間だけが伸びた。

### 対処: 2回測る

指標を1つ増やすのではなく、**測る回数を増やす**。

1. 落ち着くのを待って1回目を測る (ここには読み込み表示が写る)
2. 1回目に **新しく現れたもののうち、どれか1つが消える** のを待つ
3. もう一度落ち着くのを待って測り直す

2 が要点である。「全部が消える」を待つと、開いた領域は残るので **必ず満了する**。
何も待たなければ読み込み表示を測る。**「どれか1つ」がちょうど良い** -- 消えるのは
読み込み表示であり、残るのが開いた領域だからである。

どのセレクタが読み込み表示かは **推測しない**。「押す前には無く、押した直後に
現れた」という観測から呼び出し側が渡す (`wait_for_any_detached`)。名前で当てに
いかないのは、媒体がクラス名を変えても壊れないようにするためである。

あわせて、報告に **消えた構造** を出すようにした。待機していた領域は
`u-is-hidden` が外れる形で開くので、増えるのではなく **消える**。出さないと
その押下は「何も起きなかった」に見える。

### この回の意味

**「待つ」対策を足すときは、待っている指標が本当にその事象を表しているかを
確かめる必要がある。** ここでは指標を2つ足したのに、どちらもこの事象と無関係
だった。実行時間が3倍になったので「効いている」ようにも見えたが、伸びていたのは
満了時間である。**遅くなったことは、待てたことの証拠ではない。**

そして正解は、より良い指標を探すことではなく **同じものを2回測ること** だった。
変化する対象は、1点の観測では区別できない。
