# 実装ラダー — 媒体座標の確定手順

このシステムには **50個の未確定な媒体座標** がある。それらは実際にジョブメドレーに
ログインして観測しない限り知りようがない値であり、推測で埋めると **その推測がそのまま
送信内容と対象判定に出る**。

本書は、その座標を安全な順序で埋めていく手順書である。指示書3章のラダーに対応する。

> **各段の合格条件を満たしてから次へ進むこと。**
> 順序を飛ばすことが、この種のシステムで最大の失敗要因である。

現在の状況はいつでも次のコマンドで確認できる。

```bash
scout coordinates      # 未確定の座標を段階別に一覧 (取得方法つき)
scout preflight        # 安全弁の実効値と環境の点検
```

## 段階0: 事前調査 (コードを書く前に済ませる)

指示書4章。**実装済みのコードは、これらの答えを座標として受け取る形になっている。**

### 媒体・法務

- [x] 利用規約と自動化ポリシーの確認 — **運用者が確認済み**。
      媒体側の規約改定時は再確認する。
- [ ] 1実行あたりの送信量の上限を業務側と合意する
      → `config/config.yaml` の `send.per_run_cap_paid` / `per_run_cap_free`
- [ ] アカウント停止・凍結時の連絡経路と、その間の業務代替手段を決める
- [x] 候補者からの送信停止要求は `scout optout add <candidate_id>` で恒久除外に登録する

### 技術 (答えは座標になる)

| 調べること | 対応する座標 |
|---|---|
| 目的の画面がSPAか旧来型か | `auth.is_spa` |
| ヘッドフルでは通るがヘッドレスでは落ちるか | (挙動確認のみ。落ちるならヘッドレス判定がある) |
| Cookie+localStorage だけでセッションが復元できるか | 復元できなければセッション持ち込み方式は使えない |
| 2段階認証の種別 | `auth.twofa_kind` |
| ログイン後に追加コンテキスト(グループ選択等)が要るか | `context.selection_required` / `context.selector` |
| **画面のIDと送信APIが要求するIDが同じか** | `id.bridge_required` |
| 同じ候補者が違う表記のIDで返ることがあるか | `config.yaml` の `ids.observed_patterns` |
| 送信枠の課金・消費ルール | `api.send.paid.*` / `api.send.free.*` |
| 媒体標準の追客機能の有無と制約 | `followup.native_supported` / `followup.allowed_days` |
| **返信が実際にどの画面に現れるか** | `inbox.*` (運用者にスクリーンショットをもらうのが最短) |

## 段階1: ログインセッションの取得

**目的**: 人間が一度ログインし（2段階認証もここで突破し）、その結果を実行環境へ
持ち込めるようにする。

この段だけは**人間の操作が必ず要る**。データセンターのIPアドレスからの自動ログインは
媒体の2段階認証やボット検知で失敗しやすく、CI側で突破する手段がないからである（5.4）。

経路は2つある。**手元にPython環境が要るかどうか**が違い、成果物は同じである。

| | 経路A: ブラウザだけ | 経路B: 手元でCLI |
|---|---|---|
| 必要なもの | 普段のブラウザのみ | Python + Playwright |
| 取得できるもの | クッキー（HttpOnly を含む） | クッキー + localStorage + 属性 |
| 座標の記入 | 開発者ツールで自分で読む | コマンドが候補を印字する |

**開発も実行もクラウドで行う場合は経路Aを使う。** 以下は経路Aの手順である。

### 経路A-1: ブラウザでログインし、セッションを取り出す

何もインストールしない。普段のブラウザだけで済む。

**この操作が何をしているのか。** ブラウザが媒体に「私はログイン済みです」と伝えている
実体は、リクエストに付いている `Cookie:` ヘッダである。画面には出ないが、通信には必ず
乗っている。`Copy as cURL` は、その通信1本を **ヘッダごとテキストに書き出す** 開発者ツールの
機能である。つまり「ログイン済みの証拠」がそのまま文字列になる。それをシークレットへ
入れれば、CI側のブラウザが同じ状態を再現できる。

これが分かっていれば、途中で失敗したときにどこがおかしいのかを自分で判断できる。

#### 手順（Chrome / Edge）

1. 普段のブラウザで <https://customers.job-medley.com/customers/sign_in/> にログインする
   （2段階認証もここで突破する）
2. ログインした状態のまま **F12** を押す。画面の下か横にパネルが開く
3. パネル上部のタブから **Network**（日本語UIなら「ネットワーク」）を選ぶ
4. フィルタ欄のすぐ下にあるボタン列から **`Doc`** をクリックする
   → ページ本体のリクエストだけに絞られる。これは必ずセッションクッキーを持っている。
   **文字を打つフィルタは使わないこと**（理由は下記）
5. **F5 でページを再読み込みする**
   → ここで初めて行が現れる。**DevTools を開く前の通信は記録に残っていない**ので、
   この再読み込みが要る。この1行が「ブラウザがサーバーへ送った通信」1本である
6. 行をクリックし、右側の **Headers** パネルの **Request URL** が
   `https://customers.job-medley.com/` で始まっていることを **目で確認する**
7. その行を **右クリック** する
8. メニューの **Copy**（コピー）にマウスを合わせる → サブメニューが開く
9. **Copy as cURL (bash)**（cURL としてコピー）をクリックする
   → **画面には何も起きないのが正常。** クリップボードに入っているだけである
10. コピーした文字列を、GitHub のシークレットに登録する
    → リポジトリの **Settings → Secrets and variables → Actions → New repository secret**
    → 名前 `JOBMEDLEY_SESSION_CURL`、値は貼り付けたまま

#### なぜ文字のフィルタを使わないのか

フィルタ欄は **URL全体に対する部分一致** である。そして Google アナリティクスなどの計測
ビーコンは、**閲覧中のページURLを自分のクエリ文字列に載せて送る**。

```
https://www.google-analytics.com/g/collect?v=2&tid=G-XXXX&dl=https%3A%2F%2Fcustomers.job-medley.com%2F
                                                              ^^^^^^^^^^^^^^^^^^^^^^^^^ ここに入っている
```

したがって `job-medley` はもちろん、**`customers.job-medley.com` と完全なホスト名を
入力しても、この計測ビーコンは消えない**。実際にこの手順で最初に引っかかったのがそれだった。

`Doc` は **リソースの種類**で絞るボタンなので、この抜け道が無い。ページ本体は必ず
媒体のサーバから来るため、確実に目的の1本が残る。

正しい行かどうかは、`Type` 列が `document`、`Initiator` が空欄に近いことでも見分けられる。
`Type` が `fetch` で `Initiator` が `instrument.ts` のようなファイル名になっているものは、
計測タグが送っている通信である。

#### 間違えても、そのまま壊れはしない

宛先が媒体でないリクエストを登録した場合は、`ジョブメドレー宛ての通信ではありません`
で停止する（`handover/curl_session.py`）。`Cookie` ヘッダが無い場合も
`Cookie ヘッダが見つかりませんでした` で停止する。

**クッキーの無いセッションや他社のクッキーを取り込むと、登録だけ成功してログインだけ
復元されない**という最も気づきにくい壊れ方になるので、どちらも構造で塞いである。

#### 選ぶときの注意

- **「Copy as PowerShell」を選ばない。** 形式が違うので
  `先頭が 'curl' ではありません` で停止する
- Windows で「Copy as cURL (bash)」と「(cmd)」が出た場合は **どちらでもよい**。
  両方読める（`cmd` 形式の `^` による行継続も処理する）
- Firefox は 右クリック →「コピー」→「cURL としてコピー」で同じものが得られる

#### コピーできたか確かめる

貼り付け先がシークレット欄なので中身が見えない。不安なら一度テキストエディタに貼って
**`cookie:` という文字列が入っているか** だけを確認し、**保存せずに閉じる**。
入っていれば成功、入っていなければ別の行を選び直す。

登録後は、Actions の `Recon (manual)` → `session-check` で形式を確認できる
（媒体へは接続しない。クッキーの **名前と件数だけ** を印字し、値は表示しない）。

> **ブラウザのコンソールに JavaScript を貼る方法は使わない。**
> `document.cookie` は **HttpOnly のクッキーを読めない**ので、セッションクッキーだけが
> 欠けた「一見それらしい」出力ができる。取り込みは成功し、ログインだけが復元されない
> という、最も気づきにくい壊れ方になる。`Copy as cURL` の `Cookie` ヘッダには
> HttpOnly も含まれる。

> **貼り付ける先はシークレットだけ。** この文字列は1本で媒体アカウントに入れる。
> リポジトリのファイル、Issue、PR、チャットに貼らないこと。テキストエディタで確認した
> 場合も保存しないこと（13.2）。

### 経路A-2: 座標を観測させる

**開発者ツールで1つずつ読む必要はない。** 段階1の座標8個のうち **7個は機械で観測できる**。

**Actions → Recon (manual) → Run workflow → `observe-login`**

このコマンドは1回の実行で2つのブラウザを開く。

- **未認証のブラウザ**でサインイン画面を開き、URL・素のHTML・フォーム要素を観測する
- **認証済みのブラウザ**（保存セッション）でログアウト系の要素を観測する

この2つが要るのは、**認証済みのままではログインフォームを観測できない**（ログイン済みだと
追い出される）一方で、**未認証ではログアウトリンクが存在しない**ため。

出力はそのまま `config/site_coordinates.yaml` に貼れる形で出る。

```yaml
  auth.login_url: "https://customers.job-medley.com/customers/sign_in/"
  auth.is_spa: false
    # 素のHTMLにパスワード欄あり = 旧来型のサーバレンダリング
  auth.email_selector: "#customer_email"
    # 別案: input[name="customer[email]"]
    # 別案: input[type="email"]
  auth.password_selector: "input[name=\"customer[password]\"]"
  auth.submit_selector: "button[type=\"submit\"]"
  auth.submit_text_candidates: ["ログイン"]

  auth.success_marker_selector: "#logout"
    # 「ログアウト」に一致します
    # 別案: a:has-text("ログアウト")
```

`別案:` は捨てずに残してある。**選ぶのは人間**であり、上ほど画面変更に強い順
（`id` > `name`属性 > `type`属性、マーカーは `id` > クラス > テキスト）に並んでいる。
`css-1a2b3c4` のようなハッシュ的な名前は、ビルドのたびに変わるので候補から除外済み。

観測できなかった項目は `UNRESOLVED` のまま出力される。**空欄を「無い」で埋めない**ので、
未確定と確定済みの区別は保たれる。

### `auth.twofa_kind` だけは自分で書く

8個のうち1個だけ、機械では観測できない。

```yaml
  auth.twofa_kind: UNRESOLVED   # none / sms / totp / email_link
```

**実際に何が出たかは、その場でログインしたあなたしか知らない。** 観測できないものを
観測したことにはしないので、ここは空欄で出力される。SMSが届いたなら `sms`、認証アプリの
6桁コードなら `totp`、メールのリンクを踏んだなら `email_link`、何も無ければ `none`。

`email_link` の場合、CIで突破する手段が無いため、いま使っているセッション持ち込みが
恒久的に必須になる（自動ログインへのフォールバックが使えない）。

### 経路B: 手元にPython環境がある場合

```bash
scout recon login    # ブラウザが開く。常にヘッドフル（設定の headless は無視する）
```

**このコマンドは座標を1つも要求しない。** 段階1は座標を発見する工程なので、段階1の
座標を入力として求めると1歩目が始められなくなる。手動ログインにセレクタは不要である
——人間が自分で入力する。`auth.email_selector` などは*自動*ログイン（経路2）のための
座標であり、この段の**成果物**であって前提ではない。

ログインが終わったらターミナルで Enter を押す。**機械はログインの成否を判定しない**——
判定に使うマーカーがまだ未確定だからである。Enter の直後にセッションが保存され（5.4）、
上の表の座標のうち機械で読めるもの（`auth.login_url` / `auth.is_spa` /
`auth.success_marker_selector` の候補）が座標キー名つきで印字される。

画面の無い環境で実行した場合は、ブラウザを起動する前に停止して経路Aを案内する。

```bash
scout session export    # base64 を標準出力へ
# → GitHub の Secrets に JOBMEDLEY_STORAGE_STATE_B64 として登録する
```

両方のシークレットが登録されている場合は `JOBMEDLEY_STORAGE_STATE_B64` が優先される
（localStorage とクッキー属性が欠けていない、情報量の多い方だから）。

### 合格条件: 保存したセッションで入り直せること

クラウドで確認する場合は、GitHub の **Actions → Recon (manual) → Run workflow** から
実行する。この開発環境からは媒体へ到達できないので、判定できるのはこのワークフローだけ
である。

| 選ぶコマンド | 何をするか |
|---|---|
| `session-check` | シークレットの**形式**だけを確認する（媒体へは接続しない） |
| `verify-session` | **合格条件そのもの**。実際に入り直せるかを判定する |
| `observe-login` | 段階1の座標を観測して、記入用の値を印字する |
| `observe-list` | 段階2の残り座標を観測して、記入用の値を印字する |
| `coordinates` | 未確定の座標を段階別に一覧する |

手元にPython環境がある場合は同じことをコマンドでもできる。

```bash
scout session check                     # 形式の確認（接続しない）
scout recon verify-session              # 合格条件の判定
scout recon verify-session --headful    # 画面も開いて目視でも確認したいとき
```

判定方法は2通りあり、**どちらで判定したかを必ず印字する**。

| `auth.success_marker_selector` | 判定方法 |
|---|---|
| 記入済み | そのセレクタの有無で厳密に判定する（**これが合格条件の判定**） |
| 未確定 | ログアウト系リンクとパスワード欄の見え方による**代用判定** |

代用判定を用意してあるのは、マーカーを記入する前に「そもそも復元できるのか」を
確かめたい場面があるため。ただし代用判定は合格条件そのものではないので、マーカーを
記入したうえでもう一度実行して厳密判定で締めること。

代用判定には「判定できない」という第三の答えがある（ログアウト系の文言とパスワード欄が
両方見えた／どちらも見えなかった場合）。このとき成功にも失敗にも寄せずに非0で止まる。
**分からないことを分かったことにしない。**

| 結果 | 終了コード |
|---|---|
| 復元された | `0` |
| 復元されなかった | `10`（認証切れ） |
| 判定できない／保存セッションが無い | `20`（点検で停止） |

**撤退条件**: 復元できない場合、セッション持ち込み方式は使えない。設計を変更して
利用者に相談すること。

経路Aで失敗した場合、原因の候補は次の順で見る。

1. **認証が localStorage にある** — Copy as cURL はクッキーしか運べない。
   経路B（手元でCLI）か、開発者ツールの Application → Local Storage からの書き写しが要る
2. **クッキーが別のサブドメインのもの** — 手順3で選んだリクエストの宛先を確認する。
   このシステムは**観測したホストにだけ**クッキーを紐づける（親ドメインへ広げるのは
   「観測していないホストへセッションを送る」ことなので、意図的にしていない）
3. **セッションの有効期限切れ** — 取り直す（下記）

### セッションが切れたときの取り直し方（恒久的な保守作業）

`Copy as cURL` から作ったクッキーは**セッションクッキー**として扱われる（有効期限は
`Cookie` ヘッダに現れないので、知らないものを日付として書いていない）。媒体側の
セッションが切れれば、当然このシステムも入れなくなる。

そうなると `verify-session` が `復元されませんでした`（終了コード10）を返し、本番実行は
認証切れとして**非0で停止する**。原則2のとおり、静かに0件にはならない。

復旧手順は初回と同じである。

1. 普段のブラウザで媒体にログインし直す
2. **Doc** フィルタ → F5 → 一番上の行を右クリック → Copy as cURL (bash)
3. シークレット `JOBMEDLEY_SESSION_CURL` を**上書き**する（Update secret）
4. `session-check` → `verify-session` で確認する

**切れる周期は媒体次第なので、ここには書かない**（観測していないため）。運用しながら
実測して、このファイルに追記すること。

## 段階2: 起動前チェック

```bash
scout preflight
```

**合格条件**: 失敗項目が0件 (警告は許容)。

このコマンドは安全弁の **実効値と、その値がどこから来たか** を必ず印字する。
「環境変数で上書きしているつもりだったが実は届いていなかった」を目視で発見するため
(12.6)。

あわせて `nav.*` / `context.*` 座標を埋める。マイページ・候補者一覧のURLは段階1の
観測時に確定済み。残る座標も、**開発者ツールで1つずつ読む必要はない。**

> **2026-08-14 時点の進捗**: `observe-list` 7回の実測で `context.selection_required`
> / `context.selector` / `nav.list_ready_selector` は確定済み。残りは
> `nav.drawer_close_selectors` 1個のみ。7回目でツアーの自動完走が機能し、カードの
> クリックが初めて完了した (前進) が、`div.c-search-member-card__main-content` を
> 押しても新しい要素は出なかった -- **カードの本体クリックはドロワーを開かない**
> ことがほぼ確定した。ドロワーは「レジュメを見る」等のボタンで開くが、カードには
> ボタンが2つあり、片方は `js-tour-guide-scout-button` (スカウト送信 = 押しては
> いけない)、もう片方は文言を読まない限り用途を確定できない (13.2/13.6)。この
> 座標は **段階3の capture-send (どのみち手動・実画面) で、送信路と一緒に確認する**
> のが安全。observe-list の追加往復では確定できない見込み。
>
> なお7回目は解析の回帰も1件出した (読み込まれなかった0件ページが読み込まれた方を
> 全否定する。実害は list_ready の一時的 UNRESOLVED のみ・修正済み。
> docs/incidents.md 参照)。ランディング時にアプリDL促進モーダルが開いていることも
> 判明した (list_ready には無害だが、ドロワー観測時は閉じる必要がある)。

**Actions → Recon (manual) → Run workflow → `observe-list`**

このコマンドは保存セッションで候補者一覧URLへ直接遷移し、次を確かめる。

- 直接遷移して一覧が返るか、それとも別画面 (グループ選択等) へ転送されるか
  → `context.selection_required` / `context.selector`
- 一覧の描画完了を表す要素。**「通信の静止」を待ってはならない** ので、待つ対象と
  なる要素が要る (5.3)。年齢帯を人間が存在しない範囲にずらした変種URLと比較し、
  **0件の検索結果でも残る要素だけ**を候補にする — 行そのものを選ぶと、0件の検索を
  「まだ描画されていない」と誤読してしまう → `nav.list_ready_selector`
- 候補者を1件開き、ドロワー/モーダルを閉じるコントロールの候補
  → `nav.drawer_close_selectors` (5.7 の総当たりフォールバック用に複数個)

出力はそのまま `config/site_coordinates.yaml` に貼れる形で出る。観測できなかった
項目は `UNRESOLVED` のまま出力され、その理由 (グループ選択の先まで届かなかった・
0件比較ができなかった・ドロワーが開かなかった等) も添えて印字される。**空欄を
「無い」で埋めない**ので、未確定と確定済みの区別は保たれる。

### 値が出なかった実行も無駄にならない (構造スナップショット)

`observe-list` は、読んだDOM構造 (タグ名・クラス名・親子関係のみ。文言・id・
属性値は走査の時点で取らないので、個人データは構造的に入らない = 13.2) を
丸ごと持ち帰る。

- `artifacts/recon/structure/observe_list.json` に保存され、Actions の
  アーティファクト `recon-structure` (保持3日) としても取得できる
- 同じ内容が実行ログにも圧縮ブロックとして印字される。**運用者はこのブロックを
  貼り付ける必要はない** (開発側がログから直接回収する)
- `scout recon replay-list <ファイル>` が、保存された構造に対して **実行時と
  同一の解析** を媒体へ接続せずに再実行する

つまり、実行が UNRESOLVED で終わっても、その実行が持ち帰った実データに対して
解析を手元で直し、replay で直ったことを確かめてから次の実行を頼める。
**アルゴリズムの修正1回につき媒体への往復1回、という比例関係はもう無い。**

## 段階3: 偵察 — 実送信を物理的に禁止した状態で内部APIを特定する

### まず `follow-send` (教わった導線をそのまま辿る)

**Actions → Recon (manual) → Run workflow → `follow-send`**

**導線はもう探さなくてよい。** 運用者が実画面を示してくれた::

    一覧の「スカウトを送る」
      → 送信フォーム (左に経歴、右に入力欄)
        → **必須** スカウト対象求人 (押すと候補が出る。1件選ぶ)
        → メッセージテンプレート (任意。選ぶと本文が埋まる)
        → **必須** 本文
      → 「確認してスカウトを送る」
        → 確認の段
          → 「この内容でスカウトを送る」  ← ここで初めて送信が発火する

`follow-send` はこの順に辿る。目隠しの探索 (`capture-open`) との違いは1点だけ
で、それが決定的である -- **必須欄を埋めてから送信を押す**。埋めずに押せば
フォームは不備を訴え、送信リクエストはそもそも発行されない。実測12〜16回目は
すべてこれで終わっていた。

順序も仕様である。テンプレートは求人を選ぶと本文を自動で埋めるので、**目印は
求人を選んだ後に書かなければ上書きされる**。目印が本文に載っていることだけが、
遮断した非GETの中から送信路を観測で選び出す根拠になる (原則3)。

止まった段はそのまま報告に出る。「候補が1件も出なかった」「欄に値が入らなかった」
「無効なボタンしか無かった」は全部別の事実で、**次に直すものが違う**。

**それでも文言では指さない** (13.2)。フォームかどうかは「本文欄と押せるボタンを
同時に含む最小の領域」という形で決める。画面の文言を条件にすると、媒体が言い回しを
変えた日に静かに空振りし、ログには何も残らない (原則2)。

### 導線が変わったら `capture-open` (目隠しで探す)

**Actions → Recon (manual) → Run workflow → `capture-open`**

段階2は `nav.drawer_close_selectors` を残して終わった。理由は語彙不足ではなく
**構造的な行き止まり**である (実測5〜7回目):

- カード本体のクリックではドロワーが開かない (7回目に確定)
- 開くのはカードの中のボタンだが、片方は `js-tour-guide-scout-button`
  = **スカウト送信そのもの**。どちらがどちらかは構造からは決まらない
- 文言で分岐すれば実行ログに文言が出るし (13.2)、言い回し変更で壊れる

**押してよいボタンを観測だけで選ぶことはできない。** だから前提をひっくり返す。

`capture-open` は fail-closed の遮断を **押す前に武装** し、そのまま探索する。
武装中はGET以外すべてが記録されてから中断されるので、**どのボタンを押しても
送信は物理的に起こらない**。そして中断された非GETがそのまま段階3の成果物になる:

- ドロワーを開くボタン → 開いた領域の構造と、その中の閉じるボタン
  (**押して実際に消えたものだけ**を値にする)
- スカウト送信ボタン → 中断されたPOST = `api.send.paid.url_pattern` の観測

安全の担保はただ1点、「武装してから押す」という順序である。だから武装は探索
ループの **外側** で行い (`finally` で解除)、ループ内で武装/解除を繰り返さない。
`tests/recon/test_capture_open.py` が「全クリック時点で武装済み」「スカウト
ボタンを押しても送信されない」を固定している。

報告に出るURLは会員IDとクエリ値を伏せる (13.2)。原文は構造ダンプにだけ残る。


**副作用のある操作は、受動的な観測では絶対に取れない。** 送信APIは送信ボタンを押す
まで発火せず、押せば本当に送信されてしまう。

そこで、**送信ボタンを押す直前にネットワーク層のブロックを武装** し、以降の非GETを
記録してから中断する。

```bash
scout recon capture-send --headful
```

安全性の根拠:

- 武装中は **fail-closed で全ての非GETを止める**。段階3では送信URL自体が未知なので、
  URLやセンチネルで絞り込むのは循環参照になるうえ、payload にセンチネルが載らない
  送信を素通ししてしまう
- GET は常に素通し。武装前も素通し
- 件名・本文にセンチネル文字列を入れてある。万一送信されても内容から検知できる
- 武装ロジックは `recon/gate.py` にブラウザ非依存で切り出してあり、単体テストで
  「武装前は通す / 武装後は止める / GETは常に通す」を固定してある

出力は座標キー名に紐づいているので、そのまま
`config/site_coordinates.yaml` へ転記できる。

**埋まる座標**: `api.base_url`, `api.send.paid.url_pattern`,
`api.send.paid.payload_template`, `api.idempotency_header`, ほか

続いてレジュメのキー写像を確定する。

```bash
scout recon resume-keys
```

**キーパスだけを出力する。値は決して出さない** (13.2)。

> **最大の罠 (6.4)**: 同名キーが階層違いで別の意味を持つ。参照実装では、トップレベルの
> 「業界」「職種」が **経験してきた** もので、希望条件オブジェクト配下の同名キーが
> **希望する** ものだった。取り違えて「ご希望の◯◯業界」と書き、運用者から
> 「嘘が多い」と指摘された。
>
> **どちらか判断できない項目は UNRESOLVED のままにすること。** 空ならプロンプトに
> 出ず、モデルは言及できない。

**合格条件**: 送信APIのURL・必須ヘッダ・payload形状が特定できた。

**撤退条件**: 特定できない場合はDOM操作を再検討する (ただし2章の原則1の制約を負う)。

### 段階3-4: レジュメAPI (`recon observe-resume`)

`api.resume.url_pattern` は段階3で唯一まだ埋まっていない読み取り座標である。
埋まらなかった理由ははっきりしている — **レジュメはカードを押さないと飛ばない。**

`observe-api` は1つも押さない。押さないことがあのコマンドの安全性そのもの
だった（媒体のオリジンを丸ごと素通しにするため）。だから一覧を開いたときに飛ぶ
ものしか聴けず、レジュメはそこに入らない。

#### 押せる遮断をつくる — `GateMode.BLOCK_SEND`

| 種類 | 扱い |
|---|---|
| GraphQL | 読み取り（`query`）だけ通す。`mutation` は止める |
| REST の POST | 観測済みの読み取り経路だけ通す（`search` 系 / `label`） |
| それ以外 | 止める（他所のオリジンを含む） |

**送信は `mutation` である**（実測: `POST /api/customers/graphql/SendSingleScout`）。
だから押し間違えても、送信リクエストはサーバへ届かない。

**許可制にした理由。** 「送信のURLだけ止める」は拒否制で、知らない送信路に対して
素通しになる。許可制なら、知らないものは全部止まる。許可の中身は推測ではなく実測で、
一覧を開いたときに飛んだ REST の POST は末尾が `search` 系か `label` のものだけだった。

**残るリスクを隠さない。** 許可した経路が実は書き込みだった場合は通す。名前と
「ページを開いただけで飛ぶ」という観測が根拠であって、証明ではない。

#### 1回目の実測（2026-08-22）— 取れなかった。そして有益だった

```
押せた: label.c-checkbox.c-checkbox--blue         (新しい応答 0 件)
押せた: input.c-checkbox__input                   (新しい応答 0 件)
押せた: button.c-button.u-wd-100p.c-button--small (新しい応答 1 件)

届いた1件: POST /api/customers/members/mark_read/  {"member_ids": [...]}
           → 遮断が止めた通信に含まれる = 通していない
GraphQL は1本も飛んでいない
```

**1. 許可制が、予期していなかった書き込みを実際に捕まえた。**
`members/mark_read` はプロフィールを開くと飛び、一覧の `members[].read_profile`
を立てる。拒否制（「送信のURLだけ止める」）なら素通ししていた。

**2. 「止めたことが観測を殺した」と考えた — が、これは誤りだった。**

GraphQL が1本も飛んでいなかったので、`mark_read` を止めたせいでモーダルが
レジュメの取得まで進まなかったと推測した。**2回目の実測がこれを否定した。**

2回目は `mark_read` を止めたまま（報告は「受け入れた書き込み: なし」）レジュメを
取れている。**止めても観測できた。** 殺していたのは遮断ではなく、下の3番、
こちらの打ち切り条件だけだった。

推測を書き残しておいてよかった一例である — 次の実測が直接それを否定できた。

**3. こちらの打ち切り条件が誤っていた。** 「何か届いたら止める」だったので、
`mark_read` の（差し替えられた）空の応答で打ち切っていた。**「届いた」は
「効いた」ではない**（実測18回目と同じ間違い）。

対応は3つ。

| | 直したこと |
|---|---|
| 打ち切り条件 | 「**レジュメが**届いたら止める」へ |
| 押す対象 | チェックボックス類を外す（押しても何も開かず、予算を使うだけ） |
| 遮断 | 1回目で取れなければ、**`mark_read` だけ**を名前で受け入れて再試行 |

3つのうち **効いたのは打ち切り条件だけ**だった。2回目は1回目の試行で取れたので、
書き込みの受け入れは一度も発動していない。用意した保険が要らなかったことも観測で
ある — 外さずに残すが、発動したら報告に出る。

**受け入れる書き込みは読み取り許可リストとは別枠にしてある。** 前者は
「副作用が無いと観測できたもの」、後者は「副作用が在ると分かっていて、それでも
通すもの」。混ぜれば、受け入れた覚えのない書き込みが読み取りの顔をして増えていく。

`mark_read` を受け入れてよい根拠は、**運用者が「プロフィール確認」を押すたびに
起きている書き込みそのもの**で、立てるのは `read_profile` だけ — 送信でも、枠の
消費でも、候補者へ届くものでもない。それでも書き込みなので、行ったら報告に出す。

#### 2回目の実測（2026-08-22）— 取れた

```
押せた: button.c-button.u-wd-100p.c-button--small                          (新しい応答 1 件)
押せた: button.c-button.u-wd-100p.c-button--small.js-tour-guide-scout-button (新しい応答 2 件)
受け入れた書き込み: なし (遮断は厳しいまま)

POST /api/customers/graphql/MemberOnScoutProfileModalOfDesktop
  要求: {operationName, variables:{input:{id:<number>}}, query}
  応答: 101 キー (data.memberGet.member.*)
```

`api.resume.url_pattern` が確定した。**ただしまだ呼べない** — GraphQL の
問い合わせ文（`query` の中身）を持っていないためである。キーが在ることは
分かったが値は観測していない。送信 payload で一度同じ穴を開けている。

次は `scout recon read-bundle` が配信JSから問い合わせ文を読む（GETのみ、押下なし）。

#### 応答で新たに分かったこと

**スカウト履歴が構造化されて載っている。** 9章の重複判定と追客に直結する。

```
scoutHistories[].latestSentAt     最後に送った日時
scoutHistories[].sentCount        送った回数
scoutHistories[].latestRefusedAt  辞退された日時   ← 画面に出ていなかった
```

**候補者はスカウトを辞退できる。** 辞退された相手へ送り続けるのは最悪の失敗なので、
送信前判定に必ず入れる。ただし `null` 以外の値をまだ見ていないので、形も意味も
推測しない。

**こだわり条件が id 付きで取れる**（`desiredCondition.features[]`）。氏名が無い
以上、これが個別化の主材料になる。

**資格に取得予定フラグが付く**（`appeal.qualifications[].isScheduled`）。取得済みと
取得予定を混ぜて「◯◯をお持ちの方へ」と書くと嘘になる。

**氏名はやはり無い。** `personalInformation` に在るのは address / age / gender /
employmentStatus / recentlyRegistered の5つだけで、名前の欄は101キーのどこにも無い。

#### レジュメに何が載っているか（運用者提供の実画面）

氏名は取れない。**取れるのは会員番号のみ**で、氏名欄には「（未応募のため非表示）」が
入る。電話番号も同じ。自己PRと気になるは未入力だと「未入力」が入る。

**どれも空文字ではない。** 素直に写せば `display_name` に
「（未応募のため非表示）」が入り、モデルは「（未応募のため非表示）様」と書く。
`recon.masked.unmask()` が `None` へ落とす。取り込み経路は必ずここを通す。

個別化の主材料は **こだわり条件・資格・経験年数・希望勤務地** になる。

レジュメには「プロフィール」と「職務経歴」の2タブがあり、職務経歴側は未観測である。

#### 画面での送信の流れと、API経路との違い

```
1. カードの「スカウトを送る」
2. 「スカウト対象求人」を入力 → 「検索条件に似ている求人」から選ぶ
```

## 段階4: 応答の読み方を確定する

段階3で分かったのは **送信の投げ方** である。分かっていないのは **返ってきたものの
読み方** で、それがこの段の宿題になる。

**埋まる座標**: `api.send.paid.success_statuses`, `api.auth_failure_codes`

### この段は書き直した (2026-08-20)

以前ここには `recon dryrun-send --slot paid` を打てと書いてあった (先頭の
`scout` を省いてあるのは、**この行が実行例に見えないようにするため** である --
手順書の中の実行例は全部が実在すること、という規則を試験で守っている)。

**そんなサブコマンドは存在しない。** 打てば argparse が `invalid choice` で
終了コード2を返し、運用者は往復を1回失う。

しかも段階5の `scout dryrun` が、この段で埋まるはずの座標を要求していた。
つまり **段階4に進むための確認手段が、段階4の成果物待ち** という閉じた梯子に
なっていた。要求のほうを直した (一通も送らないコマンドは、送信の応答を解釈する
ための座標を要求しない)。同じ形の閉じ方は
`tests/guardrails/test_docs_match_the_cli.py` が禁じている。

### dryRun は「無い」ではなく「未確認」である

段階3が観測した送信の `variables.input` の中身は5つで、dryRun 相当は無い。

```
jobOfferId  jobOfferSalaryId  memberId  scoutMessage  searchUuid
```

**これが言えること**: 媒体自身のクライアントは dryRun を使っていない。
**言えないこと**: サーバの入力型が受け付けないこと。

観測したのは「画面が投げた1本のリクエスト」であって、スキーマではない。
**推測で「無い」と書かない**（原則3）。

### 4-1. 配信ファイルを読む — そして、この経路では答えが出ないと分かった

```
Actions → Recon (manual) → read-bundle
```

実測27回目の結果。**操作は7個見つかり、うち mutation は2個だった。**

```
mutation SendSingleScout($input: MessageScoutSendInput!)
mutation BulkSendScout($input: MessageScoutBulkSendInput!)
```

ここで2つ分かった。

**1. 入力型の名前は `MessageScoutSendInput` である。** このドキュメントは
`SendSingleScoutInput` と書いていたが、それは操作名から推測した名前で、
**実際の型名ではなかった**。訂正した。

**2. 一括送信の経路が在る。** `BulkSendScout` / `MessageScoutBulkSendInput` —
画面の「スカウトを送る(0/50)」がこれである。存在は確定したが、payload も
成功判定も未観測である。

**そして、この経路では dryRun の問いに答えられない。**

配信ファイルに入っているのは **操作の定義（クエリ文書）であって、スキーマでは
ない**。文書に出てくるのは変数の *型名* だけで、その型が **どんなフィールドを
持つか** は書かれていない。`MessageScoutSendInput` に dryRun 相当が在るかは、
ここからは分からない。

段階4-1 の前提そのものが誤っていた。読めば分かると考えたが、読めるのは
「何という型か」までである。

### 4-1b. スキーマに直接尋ねる (introspection・押下なし・読み取りのみ)

GraphQL には「このサーバはどんな型を受け付けるか」を尋ねる標準の問い合わせが
ある。**これは query であって mutation ではない** ので、送信は起こらない。

```
Actions → Recon (manual) → introspect
```

- 型が返った → `MessageScoutSendInput` のフィールド名が分かる。dryRun の有無が
  **送らずに** 決着する
- introspection が無効だった → それも確定した答えである。4-2 は使えないので
  4-3（少件数の実送信）へ進む

どちらに転んでも、**推測ではなく観測で次が決まる。**

#### 実測29回目の結果 — 型が返った。**dryRun は無い**

```
MessageScoutSendInput            MessageScoutBulkSendInput
  memberId          Id!            memberIds         [?]!
  jobOfferId        Id!            jobOfferId        Id!
  jobOfferSalaryId  Id!            jobOfferSalaryId  Id!
  scoutMessage      String!        scoutMessage      String!
  searchUuid        String         searchUuid        String
```

**dryRun 相当はありません。** スキーマが答えた以上、これは推測ではなく確定です。
**段階4-2 は使えません。4-3（少件数の実送信）が唯一の道です。**

**`searchUuid` は必須ではありませんでした。** 感嘆符が無い＝省略できる。以前
「一覧の応答から持ち出せなければ送信は組み立てられない」と書いていましたが、
それは観測した1本のリクエストに載っていたことからの推測でした。ただし媒体自身の
クライアントは常に送っているので、取れるときは送ります — 省いたときにサーバが
何をするかは観測していません（集計が変わるかもしれない）。

`[?]` はこちらの問い合わせの深さ不足で、**媒体の事実ではありません**。
`type { name kind ofType {…} }` と2段しか辿っていないので `[Id!]!` のような
3段の型が解けていません。一括送信を使うときに深さを足して確かめること。

### 4-2. 認証失敗の形を実測する (読み取りだけ・副作用なし)

`api.auth_failure_codes` は **送信しなくても** 分かる。失効したセッションで
**読み取りのGraphQL** を1本叩けばよい。読み取りに副作用は無い。

**GraphQL の失効は 401 でも 403 でも来ない。** HTTP 200 の本文に
`errors[].extensions.code` が入る形である (段階3で応答の作りが分かっている)。
ステータスだけを見る判定はこれを1件も拾えず、セッションが死んでいるのに例外が
上がらないまま全件が「失敗」になる -- 6.6 の事故そのものである。

> **未着手**: この観測を行う偵察コマンドはまだ無い。
> 実装するまで `api.auth_failure_codes` は UNRESOLVED のままにしておくこと。
> **ここに存在しないコマンド名を書かない** -- 前回それをやって梯子を閉じた。

### 4-3. 成功ステータスだけは、実際に1通送るまで分からない

`api.send.paid.success_statuses` は **応答を見なければ埋まらない**。そして
応答を見るには送るしかない。段階3の遮断は、まさに送らないために入れてある。

したがってこの座標は **段階6 (少件数での本番送信) の1通目で埋まる**。
それまで UNRESOLVED のままでよい。

**ただし GraphQL では、この座標の重みが参照実装より小さい。**
GraphQL は失敗しても HTTP 200 を返し、成否は本文の `errors` に書かれる。
成功判定は既に本文まで読むようにしてある (`api/success.py`) ので、
ステータスの集合は「明らかな異常 (5xx 等) を弾く」役割に縮む。

#### 実測31回目 — **失敗を運ぶ経路は3本ある**

`follow-send` が封筒ごと記録するようになり、mutation 文書そのものが取れた。

```
mutation SendSingleScout($input: MessageScoutSendInput!) {
  result: messageScoutSend(input: $input) {
    scoutedMemberId
    errorMessage        <- **これ**
    __typename
  }
}
```

| # | 経路 | 見る場所 |
|---|---|---|
| 1 | HTTPステータス | 成功集合に入っているか (6.2) |
| 2 | 本文の `errors` 配列 | GraphQL の伝送・実行時エラー |
| 3 | **本文の `errorMessage` 欄** | **媒体の業務エラー** |

**3本目は 1 も 2 も通り抜けます。** HTTP 200・`errors` 無し・それでも送れていない
応答がありうる。媒体がわざわざ選択集合に入れている以上、埋まる場面が在るという
ことです。見落とすと送信済みとして記録され、その候補者は重複送信の防止に掛かって
二度と対象になりません — **送っていないのに、送ったことになる**（原則2）。
`api/success.py` の `payload_error_paths` が3本目を見ます。

**まだ観測していないのは「どんなときに埋まるか」です。** 欄の存在は確定ですが、
失敗応答そのものは1度も見ていない（実送信をしていないので）。よって判定は保守的に
倒してあります — **空でなければ失敗**。逆向き（埋まっているのに成功とみなす）の
間違いだけは犯しません。

**送信の応答にメッセージIDはありません。** `scoutedMemberId` は会員のIDであって
メッセージのIDではない。返信の突合（10.2）は件名で行う設計なので支障はありませんが、
**会員IDをメッセージIDとして詰めない**（詰めると突合が会員IDを信じて回ります）。

**1通目で書き残すこと（3本すべて）**:

- 成功時のHTTPステータス → `api.send.paid.success_statuses`
- 成功時に `errorMessage` が `null` であること
- 失敗時に `errorMessage` へ何が入るか（**文言は座標に書かない**。候補者名が
  混ざりうるので、入るかどうかと形だけ）

#### 1通目の前に埋めるもの — 送信payloadの `<...>` は4つ

```
variables.input.jobOfferId        ← どの求人へのスカウトか      **事前に決まる**
variables.input.jobOfferSalaryId  ← その求人のどの給与条件か    **事前に決まる**
variables.input.memberId          ← 実行時に一覧の応答から取る
variables.input.searchUuid        ← 実行時に一覧の応答から取る
```

上の2つは運用者が求人を言葉で指定済みですが（ヤガサキ歯科医院 歯科衛生士 正職員）、
**IDは画面にもプロンプトにも出てきません。** 一覧を開いたときに飛ぶ読み取りの
応答にだけ入っています。

**Actions → Recon (manual) → observe-job-offers** で観測します。押しません。
送信しません。一覧を開くだけです。

このコマンドは他の偵察と違って**値を出します**。返るのは運用者自身が媒体へ
公開している求人票であり、13.2 が守ろうとしている対象（候補者の氏名・会員番号・
年齢・居住地）ではありません。伏せると、どのIDがどの求人かを突き合わせられず、
座標を埋める手段そのものが無くなります。

給与条件が複数ある場合、**どれを使うかは機械が決めません**（原則3）。報告に
並べるので運用者が選んでください。

**合格条件**: 4-1 を実行し、dryRun 相当の有無を **観測で** 決めたこと。

**撤退条件**: 4-1 で読めなかった場合、推測でスキーマを決めない。
段階5へは進めるが (空振りは送信しないので安全)、段階6の1通目は必ず人間が
結果を確認すること。

## 段階7: 上限の段階的な引き上げ

送信上限を少しずつ上げる。**同時に状態消失ガードを有効のまま保つこと。**

ここで初めて返信検知に進める。返信検知のシグナル検証には

> **10.2 の教訓**: 参照実装では受信箱の一覧行に **返信者の実名しか出ておらず、IDが
