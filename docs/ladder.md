# 実装ラダー — 媒体座標の確定手順

このシステムには **50個の未確定な媒体座標** がある。それらは実際にジョブメドレーに
ログインして観測しない限り知りようがない値であり、推測で埋めると **その推測がそのまま
送信内容と対象判定に出る**。

本書は、その座標を安全な順序で埋めていく手順書である。指示書3章のラダーに対応する。

> **各段の合格条件を満たしてから次へ進むこと。**
> 順序を飛ばすことが、この種のシステムで最大の失敗要因である。

現在の状況はいつでも次のコマンドで確認できる。

```bash
scout coordinates      # 未確定の座標を段階別に一覧 (取得方法つき)
scout preflight        # 安全弁の実効値と環境の点検
```

## 段階0: 事前調査 (コードを書く前に済ませる)

指示書4章。**実装済みのコードは、これらの答えを座標として受け取る形になっている。**

### 媒体・法務

- [x] 利用規約と自動化ポリシーの確認 — **運用者が確認済み**。
      確認日・確認者・確認したポリシーのURLを `docs/compliance.md` に記録すること。
      媒体側の規約改定時は再確認する。
- [ ] 1日あたり・1実行あたりの送信量の上限を業務側と合意する
      → `config/config.yaml` の `send.per_run_cap_paid` / `per_run_cap_free`
- [ ] アカウント停止・凍結時の連絡経路と、その間の業務代替手段を決める
- [ ] 候補者からの問い合わせ・送信停止要求の受け口を決める
      → 停止要求は `scout optout add <candidate_id>` で恒久除外に登録する

### 技術 (答えは座標になる)

| 調べること | 対応する座標 |
|---|---|
| 目的の画面がSPAか旧来型か | `auth.is_spa` |
| ヘッドフルでは通るがヘッドレスでは落ちるか | (挙動確認のみ。落ちるならヘッドレス判定がある) |
| Cookie+localStorage だけでセッションが復元できるか | 復元できなければセッション持ち込み方式は使えない |
| 2段階認証の種別 | `auth.twofa_kind` |
| ログイン後に追加コンテキスト(グループ選択等)が要るか | `context.selection_required` / `context.selector` |
| **画面のIDと送信APIが要求するIDが同じか** | `id.bridge_required` |
| 同じ候補者が違う表記のIDで返ることがあるか | `config.yaml` の `ids.observed_patterns` |
| 送信枠の課金・消費ルール | `api.send.paid.*` / `api.send.free.*` |
| 媒体標準の追客機能の有無と制約 | `followup.native_supported` / `followup.allowed_days` |
| **返信が実際にどの画面に現れるか** | `inbox.*` (運用者にスクリーンショットをもらうのが最短) |

## 段階1: ログインセッションの取得

**目的**: 人間が一度ログインし、その結果をCIへ持ち込めるようにする。

```bash
# ブラウザが開く。手で普通にログインする。2段階認証もここで突破する。
# 設定の browser.headless に関わらず **常にヘッドフルで開く** (人間が操作するため)。
scout recon login
```

**このコマンドは座標を1つも要求しない。** 段階1は座標を発見する工程なので、
段階1の座標を入力として求めると1歩目が始められなくなる。手動ログインにセレクタは
不要である — 人間が自分で入力する。`auth.email_selector` などは*自動*ログイン
(経路2) のための座標であり、この段の**成果物**であって前提ではない。

ログインが終わったらターミナルで Enter を押す。**機械はログインの成否を判定しない** —
判定に使うマーカーがまだ未確定だからである。判定できないものを判定したことにしない。

コマンドは Enter の直後にセッションを保存し (5.4)、座標の記入を助ける観測結果を
座標キー名つきで印字する。表示された値を `config/site_coordinates.yaml` に転記する。

- `auth.login_url` — 実際に落ち着いたURL（そのまま印字される）
- `auth.is_spa` — 素のHTML（JS実行前）にパスワード欄があるかで自動判定して印字される
- `auth.success_marker_selector` — ログアウト系リンクから候補を抽出して印字される。
  上ほど画面変更に強い順（id > クラス > テキスト）に並ぶので、1つ選んで記入する

残りは開発者ツールでログインフォームを検査して自分で埋める。

- `auth.email_selector` / `auth.password_selector` / `auth.submit_selector` /
  `auth.submit_text_candidates`
- `auth.twofa_kind` — `none` / `sms` / `totp` / `email_link` のどれか。
  `email_link` の場合、CIで突破する手段が無いため保存セッションの持ち込みが必須になる

`auth.success_marker_selector` は特に重要。**ログイン後にのみ存在する要素**
(「ログアウト」リンクなど) でなければならない。遷移の完了やステータスコードで
判定してはならない (5.5)。

**合格条件**: 保存したセッションを読み込んで再起動し、ログイン状態が復元される。

```bash
scout recon verify-session              # 保存セッションで入り直して確認する
scout recon verify-session --headful    # 画面も開いて目視でも確認したいとき
```

このコマンドは公開のサインインURLへ入り直して判定する。判定方法は2通りあり、
**どちらで判定したかを必ず印字する**。

| `auth.success_marker_selector` | 判定方法 |
|---|---|
| 記入済み | そのセレクタの有無で厳密に判定する（**これが合格条件の判定**） |
| 未確定 | ログアウト系リンクとパスワード欄の見え方による**代用判定** |

代用判定を用意してあるのは、マーカーを記入する前に「そもそも復元できるのか」を
確かめたい場面があるため。ただし代用判定は合格条件そのものではないので、
マーカーを記入したうえでもう一度実行して厳密判定で締めること。

代用判定には「判定できない」という第三の答えがある（ログアウト系の文言と
パスワード欄が両方見えた／どちらも見えなかった場合）。このとき成功にも失敗にも
寄せずに非0で止まる。**分からないことを分かったことにしない。**

終了コードは次のとおり。

| 結果 | 終了コード |
|---|---|
| 復元された | `0` |
| 復元されなかった | `10`（認証切れ） |
| 判定できない／保存セッションが無い | `20`（点検で停止） |

**撤退条件**: 復元できない場合、セッション持ち込み方式は使えない。設計を変更して
利用者に相談すること。

合格したら、セッションをCIへ持ち込む (5.4 経路1)。

```bash
scout session export    # base64 を出力する。CIシークレット JOBMEDLEY_STORAGE_STATE_B64 に登録する
```

**CIへの持ち込み**:

```bash
scout session export            # base64 を標準出力へ
# → GitHub の Secrets に JOBMEDLEY_STORAGE_STATE_B64 として登録する
```

## 段階2: 起動前チェック

```bash
scout preflight
```

**合格条件**: 失敗項目が0件 (警告は許容)。

このコマンドは安全弁の **実効値と、その値がどこから来たか** を必ず印字する。
「環境変数で上書きしているつもりだったが実は届いていなかった」を目視で発見するため
(12.6)。

あわせて `nav.*` 座標を埋める。マイページ・候補者一覧のURLと、一覧の描画完了を表す
要素。**「通信の静止」を待ってはならない** ので、待つ対象となる要素が要る (5.3)。

## 段階3: 偵察 — 実送信を物理的に禁止した状態で内部APIを特定する

**副作用のある操作は、受動的な観測では絶対に取れない。** 送信APIは送信ボタンを押す
まで発火せず、押せば本当に送信されてしまう。

そこで、**送信ボタンを押す直前にネットワーク層のブロックを武装** し、以降の非GETを
記録してから中断する。

```bash
scout recon capture-send --headful
```

安全性の根拠:

- 武装中は **fail-closed で全ての非GETを止める**。段階3では送信URL自体が未知なので、
  URLやセンチネルで絞り込むのは循環参照になるうえ、payload にセンチネルが載らない
  送信を素通ししてしまう
- GET は常に素通し。武装前も素通し
- 件名・本文にセンチネル文字列を入れてある。万一送信されても内容から検知できる
- 武装ロジックは `recon/gate.py` にブラウザ非依存で切り出してあり、単体テストで
  「武装前は通す / 武装後は止める / GETは常に通す」を固定してある

出力は座標キー名に紐づいているので、そのまま
`config/site_coordinates.yaml` へ転記できる。

**埋まる座標**: `api.base_url`, `api.send.paid.url_pattern`,
`api.send.paid.payload_template`, `api.idempotency_header`, ほか

続いてレジュメのキー写像を確定する。

```bash
scout recon resume-keys
```

**キーパスだけを出力する。値は決して出さない** (13.2)。

> **最大の罠 (6.4)**: 同名キーが階層違いで別の意味を持つ。参照実装では、トップレベルの
> 「業界」「職種」が **経験してきた** もので、希望条件オブジェクト配下の同名キーが
> **希望する** ものだった。取り違えて「ご希望の◯◯業界」と書き、運用者から
> 「嘘が多い」と指摘された。
>
> **どちらか判断できない項目は UNRESOLVED のままにすること。** 空ならプロンプトに
> 出ず、モデルは言及できない。

**合格条件**: 送信APIのURL・必須ヘッダ・payload形状が特定できた。

**撤退条件**: 特定できない場合はDOM操作を再検討する (ただし2章の原則1の制約を負う)。

## 段階4: dryRun付きの送信検証

媒体側に dryRun パラメータがあれば、送信枠ごとに1本ずつ検証する。

```bash
scout recon dryrun-send --slot paid
```

**ここで成功ステータスを実測する。** エンドポイントごとに違う (参照実装では通常送信が
200、他が201)。200のみを成功とみなす実装では、成功しているのに失敗扱いになる (6.2)。

**埋まる座標**: `api.send.paid.success_statuses`, `api.send.free.success_statuses`,
`api.auth_failure_codes`

`api.auth_failure_codes` はセッションを意図的に失効させて1回叩けば分かる。
**汎用の401判定だけでは403＋独自コードの形式を取り逃す** (6.6)。

**合格条件**: 期待するステータスコードが返り、権限エラーが出ない。

**撤退条件**: エラーが出る間は本番送信に進まない。

## 段階5: dry_run=true での全体実行

取り込みから生成まで通し、**送信直前で止める**。

```bash
scout dryrun --limit 5
```

**合格条件**:

- 生成文面を目視して **虚偽がない**
- 対象外になった候補者の理由が妥当

**撤退条件**: 文面に虚偽がある場合、プロンプトに禁止事項を書き足してはいけない。
指示書の原則3の通り、**モデルがそのタスクを事実だけで遂行できる情報を持っているか**
を確認する。渡していない事実について書かせれば、創作以外の選択肢がない。

数日間このまま定期実行し、生成の安定性を見ること。

## 段階6: 少件数での本番送信

```bash
# dry_run の解除は二重の明示操作が必要 (13.6)
SCOUT_DRY_RUN=false SCOUT_SEND_CAP_PAID=5 scout send --i-understand-sends-are-irreversible
```

事前に必ず:

1. `scout preflight` で **実効値を目視確認** する (dry_run=false になっているか、
   状態消失ガードが有効か)
2. キルスイッチが効くことを試す (`touch STOP_SENDING` して実行し、停止を確認)

**合格条件**: 媒体側の送信済み画面で着弾を確認できた。

確認すること:

- `send_records` に slot / subject / endpoint / 冪等キーが載っているか
- 同じ対象へもう一度実行して `ux_send_once` が弾くか
- セッションを意図的に失効させて `PermanentAuthError` が非0終了になるか

**撤退条件**: 着弾しない場合は段階3に戻る。

## 段階7: 上限の段階的な引き上げ

送信上限を少しずつ上げる。**同時に状態消失ガードを有効のまま保つこと。**

ここで初めて返信検知に進める。返信検知のシグナル検証には
「送信済みかつ確実に未返信」の実レコードが1件必要なので、**構造的に段階6より後に
しか作れない** (10.1)。

```bash
scout recon inbox --headful    # 受信箱の構造を観測する
```

> **10.2 の教訓**: 参照実装では受信箱の一覧行に **返信者の実名しか出ておらず、IDが
> 一切現れなかった**。行き詰まりを解いたのは、運用者に受信箱のスクリーンショットを
> 見せてもらったこと。返信行が「Re: 送信した件名」になっていると判明し、**件名一致**
> を突合キーにした。
>
> 画面に出ていないIDを探し続けるより、画面に必ず出ている「自分が作った一意文字列」を
> 突合キーにするほうが早い。**行き詰まったら、1枚のスクリーンショットを人間に
> 見せてもらうのが最短。**

**予備実行 (`scout-backup.yml`) は最後に足すこと。** 予備は全送信経路を二重化するので、
冪等性と `ux_send_once` が本番で証明されてからでないと、二重送信を自分で作り込む
ことになる (12.3: 順序を逆にしない)。
