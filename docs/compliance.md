### ボット検知・レート制限・CAPTCHA 検知時の縮退手順

13.6 が定義を求めているもの。**参照実装では完全に人手だった。**

1. **即時停止** — `touch STOP_SENDING` でキルスイッチを入れる
2. **間隔拡大** — `send.interval` を広げる (既定 20〜60秒)
3. **少件数で再開** — `SCOUT_SEND_CAP_PAID=5` 程度から様子を見る

送信間隔と1実行あたりの送信上限は、**ボット検知が疑われたときに調整する運用ノブ**
として設定値に出してある (5.2)。

### 対象条件のうち、法的な判断を要するもの

媒体側の検索条件は座標 `nav.candidate_list_url` に記録されており、**そのURLに
含まれる絞り込みがそのまま自動化の対象範囲になる。** ここに法的な判断を要する
条件が含まれる場合、その根拠を運用者が記録すること。

#### 性別による絞り込み (`gdr[0]=1`)

| 項目 | 内容 |
|---|---|
| 実体 | **女性のみに絞る** (運用者の申告、2026-08-12) |
| 設定箇所 | `nav.candidate_list_url` のクエリパラメータ。**本システムの `targeting` 設定には性別の条件は無い** |
| 根拠 | **ポジティブ・アクション** (均等法第8条) — 運用者の判断 |
| 判断者 | 山口 (運用者) |
| 判断日 | 2026-08-12 |

> **この根拠は運用者の判断として記録したものであり、本システムが検証したものではない。**
> 成立要件は当該職種における女性比率であり、それを知りうるのは事業主だけである。
>
> 判断の際に「媒体がこの絞り込み機能を提供している」ことが理由として挙げられたが、
> **それは法的根拠にはならない。** 均等法の義務を負うのは求人を出す事業主であって
> 媒体ではなく、媒体が機能を提供していることは事業主の適法性を基礎づけない。
> 根拠として有効なのは下記1または2に該当する事実である。
>
> 職種構成や体制が変わったときは再判断すること (**成立要件は固定ではない**)。

**募集・採用における性別を理由とする取扱いは、男女雇用機会均等法第5条の規制対象
である。** 適法となりうる主な経路は次の2つで、どちらに当たるかは運用者にしか
判断できない (自社の職種別の男女比、職務の実態を知っているのは運用者のため)。

1. **ポジティブ・アクション** (均等法第8条)
   その職種で **女性が男性と比べて相当程度少ない** 場合に、それを改善するための
   措置は許容される。判断の目安は、当該職種の労働者に占める女性の割合が
   4割を下回っていること。**優遇する側の性が少数である場合にのみ成立する**ので、
   もともと女性が多い職種では該当しない
2. **職務の性質上、一方の性でなければ本来の業務遂行ができない職務**
   均等法の指針が定める限定列挙 (防犯上の要請がある守衛等、芸術・芸能の分野、
   宗教上・風紀上の理由によるもの等)。範囲は狭い

いずれにも当たらないと判断する場合は、`nav.candidate_list_url` を性別条件なしで
取り直し、この座標を更新すること。

> **本システムは性別による絞り込みを実装していない。** 上記は媒体側の検索条件を
> そのまま引き継いだ結果であり、条件を変えるにはURLを取り直す。コード側の変更は
> 不要である。

## 3. 個人データの出口一覧と保持期間

13.2: **すべて列挙し、それぞれに保持期間を定めること。**

| 出口 | 含まれるデータ | 保持期間 |
|---|---|---|
| 状態データベース (`state/scout.db`) | 候補者ID・氏名・プロフィール分解値・文面のダイジェスト・**件名全文** | 無期限 |
| CIのアーティファクト | 分析出力 (集計値) | 14日 |
| CIのキャッシュ | 状態一式 (**資格情報は含まない**, 12.7) | 最終アクセスから約7日 |
| ローカル分析出力 (`artifacts/analytics`) | 候補者ID・氏名・集計値 | (記入する) |
| 外部スプレッドシート (使う場合) | ID・氏名・学校名・企業名 | 無期限 |
| 実行ログ (GitHub Actions) | 候補者ID・スキップ理由 | 90日 |
| **偵察の生ダンプ** (`artifacts/recon`) | **レジュメの生HTML/生JSON・フルページのスクリーンショット** | **3日** (`paths.recon_dump_retention_days`) |

### 偵察の生ダンプが最も機微である

13.2 が特に注意を促している項目。実装上の扱い:

- 保持期間を通常より短くしてある (既定3日)
- **ジョブログには構造ダイジェストのみ** を出す。生ダンプはアーティファクト限定
- 診断ログの非ASCII文字は文字数に置換してPIIを消す (`reply/diagnostics.py`)
- レジュメのキー探索は **キーパスのみ出力し、値は決して出さない**
  (`recon/resume_keys.py`)。文字列の長さすら出さない — 氏名の文字数だけでも
  識別情報になりうるため

```bash
scout purge --expired-dumps        # 期限切れの生ダンプを削除
```

### 候補者単位の削除

13.2: 「**候補者単位の削除コマンド** (DB・エクスポート・シート行の一括削除) を
用意する」。

```bash
scout purge --candidate-id <candidate_id>
```

削除すると **件名も消える** ため、以後その候補者の返信は検知できなくなる (13.3)。
削除要求に応じた結果としては、それが正しい。

### 生レジュメの保存方針

13.2 の問い: 「生レジュメの保存が本当に必要かを判断し、不要なら派生値のみ残す」。

**現在の方針: 派生値のみ残す。** `ResumeFacts` に抽出した値だけを保持し、
生レジュメは偵察時の一時ダンプを除いて保存しない。

## 4. 復旧可能期間

13.3: 「記録の保持期間が、そのまま復旧可能期間になる」。

参照実装で消えた送信記録を復元できたのは実行ログが残っていたからであり、
**件名は復元できず、その対象の返信検知は恒久的に不可能になった。**

本システムの一次記録:

| 記録 | 場所 | 書き込みタイミング |
|---|---|---|
| 宛先ID・送信時刻・枠・**件名** | `send_records` (SQLite) | **送信の直前と直後** (実行末尾に依存しない) |

実行ログとアーティファクトの保持期間 (90日 / 14日) が、**事故後に復元できる窓の
上限** である。
